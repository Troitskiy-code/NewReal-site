## 1. Остались обходы безопасного логгера в auth и подписках

Файлы и строки:

- `src/app/api/auth/register/route.ts:66,84,106` — сырые ошибки consent, signup и общего catch.
- `src/app/api/auth/reset-password/route.ts:40,89` — сырые ошибки проверки токена и изменения пароля.
- `src/app/api/auth/forgot-password/route.ts:64,69` — сырые ошибки отправки и общего catch; строка 30 также сохраняет полный email в ветке без пользователя/пароля.
- `src/app/api/subscription/cancel-recurring/route.ts:82`, `pending/cancel/route.ts:32`, `change/route.ts:147` — сырые ошибки.

Воспроизведены **настоящие функции** register.POST и reset-password.GET, с transpile текущего исходника и mock импортов. Mock БД бросает синтетическую ошибку с токеном/паролем в сообщении. Оба обработчика возвращают безопасный HTTP 500, но передают синтетический credential в console. Эти логи не проходят через новый logger.

Это проверка поведения при подставной ошибке, а не утверждение о фактической утечке production-секрета. Она доказывает отсутствие защиты в ветке, куда могут попадать сообщения Prisma с аргументами запроса и ошибки провайдеров.

**Что исправить:** провести эти catch через диагностический путь со строгим разрешённым набором полей. Проверить оставшиеся чувствительные auth/payment/Prisma места вызова, включая sitemap. Бизнес-логику и P1 не менять. Добавить тесты фактических handlers с секретами в подставных ошибках; helper-тесты и поиск строки в auth.ts этих веток не покрывают.

## 2. `toSafeDiagnostic` очищает произвольное значение вместо ограничения полей ошибки

`src/lib/safeDiagnostics.ts:4–5`: helper вызывает `redactSensitive(error)`. Это безопасно для распознанного Error/Prisma/Axios/OAuth, но обычные объекты и строки сохраняются иначе.

Независимо воспроизведено:

- `reportAuthFailure` с обычным объектом `{ message: SYN, stack: SYN, meta: { queryArgs: SYN } }` сохраняет все эти значения в console и mock Logtail.
- `reportPrismaFailure` с не-Error строкой `SYN` сохраняет строку в обоих каналах.

Следовательно, утверждение «ошибки идут через безопасные поля без message/stack/meta/config» верно только для части распознанных форм. Название helper не гарантирует его контракт для `unknown`.

Дополнительно: `safeIdentifier` в `src/lib/redactSensitive.ts:45` ограничивает символы и длину, но это не перечень допустимых кодов/имён. Синтетический секрет, состоящий из разрешённых символов, сохраняется в Error.name; такая проверка полезна для формата, но не доказывает безопасность произвольного значения.

**Что исправить:** отделить сериализацию обычного лог-контекста от обработки ошибок. Для ошибок возвращать фиксированную категорию, подтверждённый код/HTTP status и разрешённые поля; неизвестные строки/объекты — фиксированная категория без содержимого. Сделать fallback безопасным при getter/proxy/сбое сериализации. Для имён/кодов использовать известные категории или проверенные перечни/форматы конкретного провайдера, а неизвестные значения опускать. Не пытаться сделать произвольную внешнюю ошибку безопасной только regex.

## 3. JSON-строки обходят scrub, а Robokassa логирует response body

`src/lib/redactSensitive.ts:16–17`: ASSIGNED_SECRET ожидает разделитель сразу после имени ключа. В `{"password":"SYN"}` после имени стоит закрывающая кавычка, поэтому значение сохраняется. Это подтверждено через настоящий `errorLog` и mock Logtail.

Рабочие места использования внешних тел:

- `src/lib/robokassa.ts:354` — тело неуспешного recurring charge.
- `src/lib/robokassa.ts:398,403` — тела неуспешной и успешной отмены recurring.

Вызван настоящий `chargeRobokassaRecurring` с **mock fetch**: ответ HTTP 400 с JSON-полем password и синтетическим значением. Ожидаемое исключение бросается, но credential одновременно остаётся в console и mock Logtail. Реальных HTTP-вызовов/платежей не было. Это доказательство поведения при чувствительном теле ответа, не утверждение, что Robokassa действительно возвращала такие данные в production.

**Что исправить:** убрать сырой responseText из платёжных логов; оставить постоянное событие, status и необходимые внутренние идентификаторы. JSON scrub добавить как дополнительную защиту с тестами на ключи в кавычках/несколько секретов; он не заменяет отказ от логирования произвольных provider bodies. Проверить `renew-subscriptions` summary: results могут содержать текст ошибки, поэтому свести лог к разрешённому резюме.

## 4. Сканер не проверяет весь кандидат коммита

`scripts/verify-p0-security.ts:302–354` сканирует фиксированные каталоги и несколько корневых файлов, с ограниченным списком расширений. Это не инвентаризация через Git tracked + untracked/staged. Корневые конфигурации, YAML/TXT/LOG и другие файлы могут быть пропущены. Подстрока `your_` делает всю строку placeholder_ok; `verify-` исключает часть проверок; ошибка чтения каталога становится skip.

Независимый regression probe создал временный **синтетический** корневой JSON-файл с маркером формы live-key, который собственное правило сканера должно отклонить. Git включил файл в список неигнорируемых untracked кандидатов; сканер всё равно вернул exit 0 и «Passed 61 checks». Файл удалён в finally. Реальный ключ не использовался.

**Что исправить:** получать файлы кандидата из Git, читать рабочие и staged версии согласно выбранному режиму, покрывать поддерживаемые конфигурации/текстовые файлы и не превращать ошибку чтения в успех. Исключения разрешать для конкретного очевидного fixture/значения, а не всей строки по подстроке. Добавить тест сканера с заведомо обнаруживаемыми синтетическими fixtures. В отчёте описывать границы сканера; успех не доказывает отсутствие любых возможных секретов.

## 5. Уточнить runbook перед выполнением ротации

Production-ротация правильно отделена от исправления кода и не объявлена выполненной. План выхода старых сессий и отказа старого пароля на новом соединении полезен.

Однако таблица потребителей утверждает, что DIRECT_URL используется Prisma CLI/migrate. В текущей `prisma/schema.prisma` datasource имеет только `url = env("DATABASE_URL")`, без `directUrl`; `prisma.config.ts` отсутствует. Само наличие DIRECT_URL в панели не переключает CLI. При этом `scripts/translate-characters.ts`, `scripts/backfill-character-slugs.ts` и другие служебные скрипты действительно читают DIRECT_URL явно.

Уточнить фактических потребителей, команды и конфигурацию CLI. Не менять схему/платформу ради документа. Формулировка о старых логах/истории должна говорить: ротация **отзывает** раскрытые credentials, но **не удаляет** их исторические копии. Возможность окна обслуживания и порядок действий проверить у оператора; из репозитория нельзя подтвердить функции панели хостинга.
