# Задание Cursor: Метрика при покупке подписок/VC + защита логгера от циклов

Выполни исправления в текущем проекте. Основная задача — надёжная клиентская аналитика подтверждённых покупок при задержке/недоступности Яндекс Метрики. Включи небольшую оставшуюся правку обхода циклов в logger. Остальные P1 и экономика вне области работы.

## 1. Исходные проблемы и границы

Прочитай актуальные файлы и следующие доказательства:

- `docs/metrika-purchase-review.md`, `.cjs`, `.json` — ошибки fallback и ложной готовности ym, прежнее браузерное воспроизведение.
- `docs/p0-security-third-independent-review.md` и `docs/p0-security-logger-cycle-probe.cjs` — зависание нового error formatter на циклическом массиве.

В F12 наблюдалось `GET https://mc.yandex.ru/metrika/tag.js net::ERR_CONNECTION_CLOSED`. Это загрузка внешнего счётчика. По этой строке нельзя установить, кто закрыл соединение. Код не может гарантировать доступность домена у всех посетителей; отказ первого запроса может остаться в F12 при успешной резервной загрузке. Не ставь критерием приёмки «скрыть красную строку» и не объявляй блокировку доказанной без диагностики.

Подтверждённые ошибки приложения:

1. В `YandexMetrika.tsx` fallback меняет src уже использованного script; прежний браузерный probe не увидел нового запроса.
2. ym-очередь создаётся до tag.js. `waitForMetrika` проверяет только typeof ym; `reachGoal` возвращает true при queue push. Tracker записывает «уже отправлено» и удаляет query, хотя библиотека не загружена.
3. Подтверждение ожидается около 24 секунд, затем аналитика не возобновляется при позднем webhook. Тип/план берутся из query, а сервер отвечает только status/invId.

Не меняй цены, VC, экономику, подпись Robokassa, начисления, гостевые лимиты/перенос, поддержку и другие UX-задачи. Не выполняй production-ротацию, миграции на production, релиз, реальные списания/письма, изменение кабинета Метрики, commit/push. Сохрани чужие изменения и уже исправленный контракт безопасных логов.

## 3. Исправить загрузку и readiness

- Создавай **новый script-элемент** для fallback с отдельными обработчиками. Не ограничивай исправление сменой порядка `.ru`/`.com`. Используй официальные источники скрипта; не добавляй прокси/зеркала для обхода ограничений.
- Один загрузчик и один init конкретного counterId на документ, включая remount, React StrictMode и навигацию. Не затирай существующую очередь и корректно обработай уже готовый счётчик.
- Раздели состояние загрузки библиотеки и инициализации счётчика. Наличие ym и onload скрипта не считаются готовностью нужного counterId. Зарегистрируй listener до init, используй документированный сигнал; сохрани readiness для поздних подписчиков.
- Ограничь попытки, таймауты и обработчики; после неудачи обоих источников не запускай бесконечное создание scripts. Возобновление после восстановления сети допускает ограниченную новую попытку с backoff. Учитывай запоздавшие события предыдущей попытки, чтобы не делать двойной init.
- Ошибка загрузки не должна ломать страницу, оформление, подтверждение оплаты или начисление. Не подавляй глобально console/network errors; диагностические события должны отражать фактическое состояние.

## 4. Отправка целей без ложного успеха

- Для покупки различай как минимум pending confirmation, ready to dispatch, dispatched, callback completed и timeout/unknown result. Queue push не означает доставку. Не записывай финальное sent=true до выбранного подтверждённого клиентского результата.
- Обрабатывай callback reachGoal и ограниченный таймаут. Callback — сигнал клиентской отправки согласно API, не гарантия появления конверсии в кабинете. Невозможно обещать exactly-once доставку внешней аналитике при потере ответа; опиши политику повторов и ограничения.
- Сохрани существующие идентификаторы: подписка — `subscription_success` и соответствующая `subscription_dialog` / `subscription_history` / `subscription_universe`; VC — `vc_purchase_success`. DB `story` отображается в `history`. Две цели подписки учитывай раздельно: подтверждённую callback-цель не посылай снова при повторе второй.
- Проверка счётчика и сбои покупок не должны сломать остальные цели: login/register, send_message, character и другие существующие вызовы. Проверь и обнови потребителей изменённого API.

## 5. Источник истины о покупке

- Сохрани обязательные invoiceId и server-confirmed PaymentEvent текущего пользователя. `payment=success`, подставленные type/plan/InvId и callback библиотеки не подтверждают покупку.
- Расширь `/api/payment/status` минимальными разрешёнными сведениями о **конкретной подтверждённой покупке**, чтобы клиент не выбирал вид цели и план из произвольного query. Сохрани проверку владельца, не раскрывай чужие события. URL используется только для поиска invoice.
- Сейчас PaymentEvent хранит kind, но не исторический planId/сумму. Не выводи план покупки из текущей подписки пользователя и не считай Transaction.amount ценой в рублях: там могут храниться VC/ноль. Если для корректных плановых целей нужна запись analytics metadata, разрешено подготовить минимальное **добавочное** nullable-поле/поля и миграцию, записываемые в существующей транзакции после проверки webhook. Не меняй начисления/подпись/уникальность; production-миграцию не выполняй. В отчёте явно укажи зависимость выпуска от миграции и порядок применения.
- Исторические события без сведений обрабатывай безопасно: неизвестный план не превращается в произвольную плановую цель. Не выдумывай backfill по текущему тарифу пользователя. Отличай subscription purchase/pending от автоматического renewal; renewal не должен случайно считаться новой покупкой по пользовательскому URL.
- Передача дохода не обязательна для этой задачи. Если добавляешь order_price/currency, бери фактическую подтверждённую сумму, передавай доход только в одну основную purchase-цель, чтобы не удвоить его между двумя целями подписки. Если достоверной суммы нет — опусти её и опиши ограничение.

## 6. Восстановление, поздний webhook и защита от дублей

- Сохраняй минимальное pending-событие до потери исходных query-параметров. Можно очищать только платёжные query после успешного сохранения восстановимого состояния либо завершения обработки. Сохрани остальные query/hash и locale-path. При недоступном storage не теряй единственный способ восстановления молча.
- Pending-состояние должно переживать reload, уход/возврат и восстановление библиотеки. Задай срок хранения, предел событий/попыток и backoff; без токенов, паролей, email, тела webhook и полной платёжной ссылки в storage/логах. Минимум: invoiceId, необходимые подтверждённые сведения, состояния целей и время/попытки.
- Возобновляй подтверждение позднего webhook после нынешних 24 секунд: bounded polling плюс повтор при focus/online/возврате или иной понятный механизм. Отдельно обрабатывай 401/5xx/offline, не выдавай их за confirmed.
- Общий механизм подтверждения для баннера и аналитики не должен расходиться по invoice/status. Можно вынести общий hook/service; не меняй оплату и не переписывай UI.
- Возобновление не зависит от повторного наличия SubscriptionPlans. Подключи единственный обработчик pending-покупок в подходящем общем клиентском месте. Исключи параллельных отправителей при двойном mount и двух вкладках доступным межвкладочным механизмом; зафиксируй пределы при запрещённом storage.
- Ключ дедупликации: counterId + provider/invoiceId + **отдельная цель**. Не используй запасной invoiceId="ok". Перед возобновлённой отправкой проверяй серверное подтверждение и текущую сессию. Logout/смена аккаунта отменяют активную работу и исключают применение старого async-ответа к новому пользователю.
- При неопределённом исходе callback задай ограниченную политику retry и опиши возможный дубль. Не объявляй локальную дедупликацию глобальной гарантией Яндекса.

## 7. Одновременно исправить цикл логгера

В `src/lib/logger.ts` у `formatErrorLogArg` нет seen/depth. Случай `const a=[]; a.push(a,a)` зависает в ограниченном независимом probe; прежний redactor с WeakSet для этой ветки не используется.

Добавь защиту от повторного посещения **до** обхода массива/Map, лимит глубины и общий бюджет/объём. Либо безопасно отклоняй неизвестные контейнеры ошибок. Не возвращай сырые message/stack/error и не отменяй allowlist. Циклы, превышение лимита и сбои getters дают фиксированные безопасные заглушки, логирование завершается быстро.

Добавь регрессии настоящего formatErrorLog/errorLog: один и два self-reference, смешанный цикл, Map, глубокий/ветвящийся контейнер, console/mock sink. Потенциально зависающий случай тестируй дочерним процессом с timeout. `node docs/p0-security-logger-cycle-probe.cjs` должен дать completed=true/exit=0/timedOut=false в обоих случаях. Производственные секреты не используй.

## 8. Проверки и приёмка

Создай воспроизводимые `verify:metrika` и браузерную проверку Playwright либо равноценные команды. Браузер должен выполнять фактическую React/Next-интеграцию, не только заменённый useEffect. Все домены аналитики перехватывай до открытия страницы; никаких событий в боевой счётчик 112171267. Используй mock tag/init/reachGoal с управляемыми событиями/callback и отдельное тестовое API/БД. Не поднимай приложение с production URL из `.env`.

Обязательные сценарии:

1. Primary работает: один script/init; после server confirmation VC — одна цель, подписка каждого из трёх планов — две нужные цели. Проверь RU/EN.
2. Primary ERR_CONNECTION_CLOSED, fallback доступен: браузер делает **новый запрос** к fallback, правильный init и отправку. Принимается исходная ошибка primary в F12.
3. Оба источника недоступны: покупка не зависит от аналитики, нет ложного sent, событие остаётся восстановимым. После reload/online восстановление завершается.
4. tag.js задерживается; очередь ym уже есть: readiness=false до реального init. Поздний подписчик видит готовое состояние; повторный mount не создаёт init.
5. Webhook подтверждает позже 24 секунд; tracker переживает переход со страницы и возврат; баннер и аналитика используют одинаковое подтверждение.
6. Reload, StrictMode, параллельные вкладки: завершённые цели не повторяются. Callback первой subscription-цели успешен, второй задержан/потерян: повтор касается только незавершённой согласно политике.
7. Подмена URL type/plan, чужой invoice, отсутствие invoice, 401/5xx, logout и смена аккаунта: ложных/чужих целей нет. Поздние ответы отменённой попытки не активируют отправку.
8. Storage запрещён/повреждён/переполнен; callback не пришёл; истёк TTL: безопасный ограниченный fallback и честный статус, без бесконечных повторов. Неплатёжные query/hash сохраняются.
9. Ранее найденные утечки и цикл нового логгера не воспроизводятся. Staged-only ключ обнаруживается, staged deletion проходит.

Выполни проверки Метрики, `verify:p0-security`, `verify:p0-p1`, оба независимых P0 harness, cycle probe, TypeScript, lint изменённых файлов, diff check и сборку с синтетическими env. Если добавлена миграция — проверь только на принадлежащей тесту локальной БД с историческим nullable fixture; не используй опасный старый default интеграционного скрипта с остановкой чужого процесса.

Сохрани отчёт `docs/metrika-purchases-fix-report.md`: изменённые файлы, состояния/политика retry, фактические browser requests/init/goals/callback, команды/результаты, зависимость от миграции и честные ограничения. Существующие independent harness не ослабляй: при изменении интерфейса подготовь новый regression runner и опиши адаптацию.

Кабинет Яндекса без доступа не считается проверенным. Подготовь отдельный краткий ручной чеклист для владельца: counterId, наличие целевых событий с указанными именами, `_ym_debug`, тестовый счётчик и последующая проверка отчёта. Не создавай цели и не отправляй тестовые покупки в production из агента. Production-ротация P0 остаётся pending до оператора.

Выполни код и проверки в этой задаче; не ограничивайся планом. Не расширяй scope на остальные P1, тарифы и экономику.
