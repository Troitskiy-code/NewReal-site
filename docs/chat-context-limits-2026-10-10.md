# Согласование контекста чата и тарифов — 10 октября 2026

## Проблема и решение

Девять существующих моделей в seed и пять подготовленных тестовых моделей имели maxContextTokens=12000. В приложении это потолок суммы входа и зарезервированного выхода. Поэтому тариф Вселенная с обещанным входом 16000 фактически ограничивался 11000, а Aion 3.5 Mini с выходом 4000 — 8000.

Для всех 14 известных моделей подготовлен потолок приложения 20000. Он вмещает 16000 входа и самый большой настроенный выход 4000. Это не нативная вместимость модели. В сегодняшнем снимке публичного каталога KodikRouter, полученном другим чатом (`roleplay-model-catalog-2026-10-10.json`), у всех перечисленных моделей окно не меньше 128000; приложение сознательно использует меньший потолок.

Тариф ограничивает весь входной промпт: инструкции персонажа, память, историю и последнее сообщение вместе. Старт/Диалог — до 6000; История — до 10000; Вселенная — до 16000. Вход вычисляется как min(лимит тарифа, maxContextTokens модели − настроенный max_tokens выхода). Объём фактической истории также ограничивают её доступность и лимиты количества сообщений. Лимиты — потолки, каждый запрос не обязан их заполнять. Подсчёт входа остаётся существующей оценкой токенизатора приложения; provider usage нужен для проверки фактического расхода.

Гостевой путь раньше брал окно модели минус 400, хотя выход равен 1000. Он теперь использует общий расчёт бесплатного тарифа: максимум 6000 входа с резервом фактического выхода. Тестовые модели исключены из гостевого fallback, как из обычного базового выбора.

## Подготовленные изменения

1. `20261010190000_chat_testing_models/migration.sql`: пять тестовых моделей создаются/обновляются сразу с окном 20000.
2. `20261010200000_chat_context_limits/migration.sql`: меняет только maxContextTokens для 14 конкретных имён. Сохраняет id, цены, активность, описания и выбор пользователей; не трогает неизвестные модели. Повторяемый SQL не создаёт дубликаты.
3. `prisma/seed.js`: девять прежних моделей для нового окружения имеют окно 20000. На production этот seed запускать нельзя: он по-прежнему удаляет модели и сбрасывает пользовательский выбор.

Цена VC за ответ и тарифы не менялись. Более длинный фактический вход может увеличить рублёвый расход, поэтому предварительные цены тестовых моделей необходимо оценивать по AiCostEvent при длинных диалогах, особенно на Вселенной. Фиксированные 38 VC у Aion 3.5 не доказывают достаточную маржу.

## Применение

Production не изменён. Сначала выложить код с ограничением гостевого контекста, затем после актуального бэкапа применить оба SQL по порядку одной транзакцией в Adminer. Это не расширяет гостевой вход между увеличением окна в БД и выкладкой исправления. При ошибке выполнить ROLLBACK; не фиксировать частичное обновление. При настроенной истории миграций можно использовать штатный deploy; не создавать фиктивную историю старых миграций ради этой задачи.

После SQL проверить список известных имён в Model: все 14 должны иметь maxContextTokens=20000. Проверить список моделей и диагностируемый вход на каждом тарифе. Проверить выход и reasoning Aion через реальные usage. Не открывать платный тестовый вызов без отдельного согласования.

## Проверки

`verify:models:testing` проверяет реальную тарифную функцию для 14 моделей на четырёх тарифах, истёкшую подписку, гостевую точку вызова и её fallback, обычный/stream запросы, повторное исполнение обоих SQL в PGlite. Проверка сравнивает все поля старых строк и связанный выбор до/после обновления окна. PGlite не заменяет проверку production PostgreSQL или платного шлюза.

Проверки пройдены: verify:models:testing — PASS; verify:memory — 67 passed, 0 failed; TypeScript — exit 0; ESLint изменённых файлов — exit 0, только два прежних предупреждения img; git diff --check — exit 0. Перед выпуском повторно выполнен npm run build (Prisma generate + Next build) с синтетическими БД, секретом сессии и счётчиком 999001: exit 0, 69 страниц. Первая попытка остановлена файловым ограничением EPERM; повтор с разрешённым доступом завершился успешно. Production-БД и реальные AI не использовались.

Сверка кода, SQL и отчётов выполнена перед коммитом по запросу владельца. SQL в production пока не применён; push кода не подтверждает успешный автоматический деплой. Cursor должен проверить выкладку, обновить бэкап и применить оба SQL одной транзакцией.
