# Метрика при покупке подписок и VC — 1 октября 2026

**Вывод:** `GET https://mc.yandex.ru/metrika/tag.js net::ERR_CONNECTION_CLOSED` относится к загрузке внешней библиотеки Метрики, а не к начислению покупки. В коде при этом есть две ошибки, из-за которых подтверждённые покупки могут потеряться в аналитике: неработающий fallback и фиксация успеха до реальной готовности счётчика.

Код приложения не исправлялся. Проверены исходники, публичный HTML newvers.ai и изолированный Edge/Chromium с перехваченными запросами и подставленным server-confirmed платежом. Настоящие цели/платежи не отправлялись. Кабинет Метрики и настройки целей не проверялись.

## Откуда ошибка

`src/components/YandexMetrika.tsx` динамически создаёт script с tag.js. Компонент находится в RootLayout, поэтому библиотека загружается на страницах сайта независимо от покупки. `VM26:8` указывает на исполняемый встроенный скрипт; GET tag.js не является запросом оформления/начисления VC.

Адрес `.ru` является штатным адресом Яндекса: [инициализация счётчика](https://yandex.com/support/metrica/ru/code/counter-initialize). По одной строке ERR_CONNECTION_CLOSED нельзя определить, кто закрыл соединение. Яндекс перечисляет среди причин недоступной Метрики расширения, firewall и блокировку домена в hosts: [проверка цели](https://yandex.com/support/metrica/ru/general/check-goal?lang=ru). Это возможные причины, а не доказанный диагноз конкретного браузера пользователя.

Во время проверки локальный загрузчик изменился: теперь primary — `mc.yandex.com`, fallback — `mc.yandex.ru`. Простая перестановка доменов не устраняет ошибки ниже. Публичный HTML newvers.ai/ru отвечает 200 и содержит оба адреса; параметра triggerEvent в нём нет. HEAD-запросы к обоим tag.js из этой среды завершились HttpRequestException; это не доказывает недоступность Яндекса у всех посетителей.

## 1. P1 — fallback не запускает новый запрос

Обработчик делает `k.src = fallbackUrl` на уже использованном script-элементе. В изолированном браузере primary принудительно завершается ERR_CONNECTION_CLOSED, fallback доступен через заглушку. Зафиксирован **только один запрос к primary**; запрос к fallback не возникает. Контроль с созданием нового script-элемента успешно загружает тот же fallback.

Такое поведение согласуется с флагом already started при подготовке script: [HTML Standard](https://html.spec.whatwg.org/multipage/scripting.html#prepare-the-script-element).

**Исправить:** создавать новый script для резервной загрузки, с отдельными onload/onerror, защитой от дублей и конечным числом попыток. Даже успешный fallback не удаляет уже записанную браузером ошибку первого запроса из F12. Не скрывать проблему только изменением домена.

## 2. P1 — очередь ym считается готовым счётчиком

`src/lib/metrika.ts:93–100` проверяет только typeof window.ym. Загрузчик создаёт ym как очередь **до загрузки tag.js**. Поэтому waitForMetrika немедленно возвращает true, даже когда библиотека не загружена.

`reachGoal:77–90` возвращает true после вызова этой очереди. В `goalTracking.ts:111–115` это ведёт к записи sessionStorage «уже отправлено» и очистке параметров оплаты из URL.

Воспроизведено для VC и подписки с подтверждённым mocked PaymentEvent:

- tagLoaded=false;
- waitForMetrika=true;
- actualLibraryCalls=0;
- markedFired=1;
- queryCleared=true;
- события остаются только в ym.a: init + VC goal либо init + две subscription goals.

Если библиотека позже реально загрузится, очередь потенциально может обработаться; сам факт queue push не доказывает доставку. При окончательном отказе библиотеки новая загрузка страницы уже не содержит параметров покупки, и цель теряется. Логи `sent: true` вводят в заблуждение.

**Исправить:** отслеживать реальную инициализацию счётчика; Яндекс документирует init с triggerEvent и событие yacounter…inited. Сохранить различие queued / dispatched / callback-completed. `reachGoal` имеет callback ([документация](https://yandex.ru/support/metrica/ru/objects/reachgoal)); он полезен для результата клиентской отправки, но не является гарантией появления конверсии в отчёте.

Не фиксировать final «отправлено» и не удалять данные для восстановления сразу после постановки в очередь. Сохранить минимальное pending-событие с invoiceId и типом покупки, без секретов/PII; после восстановления повторять с определённой защитой от дублей. Учитывать две цели подписки отдельно: одна может отправиться, другая — нет.

## 3. Что сейчас вызывается при покупке

- Подписки: `subscription_success` с plan; затем `subscription_dialog`, `subscription_history` или `subscription_universe`. DB story сопоставляется с history.
- VC: `vc_purchase_success`. На /coins tracker подключается через встроенный SubscriptionPlans, где вызывается usePaymentGoal. Поэтому отсутствие прямого usePaymentGoal в CoinsPage не означает отсутствие VC-цели.
- Требуется InvId и confirmed от `/api/payment/status`; один payment=success без InvId цель не отправляет. Endpoint проверяет, что PaymentEvent принадлежит текущему пользователю.

Это полезное отличие от отправки цели просто по SuccessURL. Но цикл подтверждения ограничен 12 попытками с паузой 2 секунды (примерно 24 секунды). После позднего webhook текущий tracker сам не возобновляет отправку. Баннер имеет отдельное более длинное ожидание; возможно состояние «покупка подтверждена» без отправленной цели.

Тип/plan события берутся из query string, а API возвращает только status/invId. Для достоверной классификации цели стоит возвращать разрешённые серверные сведения о подтверждённой покупке. Текущее sessionStorage-dedup ограничено вкладкой/сессией браузера и не даёт глобальную защиту от повторного учёта.

Идентификаторы целей должны существовать в счётчике 112171267 как целевые события; этот факт из исходников проверить нельзя. Доход покупки сейчас не передаётся в goal params как order_price/currency. Это не вызывает ERR_CONNECTION_CLOSED, но важно, если ожидался отчёт по суммам покупок.

## Критерии исправления

1. Primary работает → один init, нужные цели после server confirmation, нет дублей при reload/remount.
2. Primary падает, fallback работает → новый script/request, реальный init, цель отправляется; console-error primary может остаться.
3. Оба адреса падают → покупка работает независимо от Метрики; нет ложного sent=true, pending-событие восстанавливается позже.
4. tag.js загружается с задержкой; webhook приходит позднее 24 секунд → подтверждённая покупка не теряется.
5. Проверить подписки dialog/story/universe и VC, RU/EN, reload и уход/возврат на страницу. Тестовые цели отправлять только в отдельный тестовый счётчик либо перехватывать в браузере.

Доказательства: `docs/metrika-purchase-review.cjs` и `docs/metrika-purchase-review.json`. Harness использует настоящий DOM-загрузчик и скомпилированные metrika/goalTracking; React hooks заменены минимальными заглушками, все requests перехвачены. Это воспроизведение клиентской логики, не реальная доставка в кабинет Яндекса.
