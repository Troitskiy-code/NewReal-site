параллельным исследованием не менялись. Живых AI-диалогов и сравнительного
теста моделей не было.

При внесении дополнения прочитаны все 112 блоков Word, включая таблицы.
В файле нет изображений, комментариев или исправлений с отслеживанием;
сноски и концевые примечания пусты. Наличие указанной исходной CSV-выгрузки
в Документах проверено, но её строки заново не классифицировались.
Числа кабинета, результаты офлайн-скриптов и отправка переобхода ниже —
данные предоставленного отчёта, не повторная проверка кабинета автором дополнения.

Отдельно просмотрены текущие `seoIndexing.ts`, layout `/coins`, loader Метрики,
`purchaseGoalRuntime.ts`, основной chat handler, `chatHelpers.ts`,

## SEO-01 Что удалось установить

В снимке 8 октября 1896 исключённых URL:

- 1622 дубля; 1609 из них — варианты `/ru` и `/en` с `etext`/`ybaip`.
- 130 малоценных; 128 — рекламные варианты адреса, ещё чат и возврат из оплаты.
- 69 ожидаемых noindex-исключений ссылок подтверждения email.
- 44 OTHER; группы разобраны: рекламные параметры, фильтры, ошибки OAuth,
  возвраты из оплаты и служебные страницы. Это заменяет старое ожидание
  выгрузки 141 «неизвестного исключения».
- 29 BAD_MIME_TYPE — URL API аватаров, возвращающие изображения. Сам по себе
  статус не требует превращать изображение в HTML или менять правильный MIME.
- Один HTTP_ERROR `/ru/preload` и один redirect `/preload` на этот 404.

В поиске 442 URL: 208 с рекламными параметрами (205 с `etext`), 106 карточек,
79 чатов, 25 основных страниц, 21 приватная/служебная страница, два возврата
из оплаты и один адрес сброса пароля с токеном. Это классификация отчёта,
не число пользователей или утечек переписки. Истёкший reset token не доказывает,
что он был безопасен в момент первого попадания к роботу.

По отчёту все 1622 дубля обнаружены через обход по Метрике, а не из sitemap.
Исправления canonical/Clean-param/noindex опубликованы 4 октября (`bebc077`),
а большая часть проблемных URL последний раз обходилась раньше. Поэтому старый
состав поисковой базы не доказывает неисправность текущих canonical.

Sitemap в новом снимке содержит 254 URL; 116 пересекаются с поиском.
В отчёте отдельно выделены 137 отсутствующих карточек. Эти множества нельзя
вычитать из общего числа 106 карточек в поиске без проверки совпадения URL:
группа страниц в поиске и пересечение с каноническим sitemap — разные показатели.

## SEC-04 P1 Приватность возвратов из оплаты

Обновление после реализации: SEC-04 исправлен в рабочей копии и прошёл локальную
HTTP/браузерную приёмку; выкладка, проверка фактической библиотеки/счётчика и
удаление старых URL из поиска остаются. [Изменения, проверки и ограничения](sec-04-url-privacy-2026-10-08.md).
Диагноз и требования ниже относятся к состоянию до этих исправлений.

В отчёте два URL `/coins` с платёжными параметрами находятся в поиске,
а такой возврат на действующем сайте отвечает `index, follow`.
В проверенном до исправления коде обычный `/coins` и вариант с платёжными параметрами получали
одинаковую политику: `src/app/coins/layout.tsx` вызывает общую metadata,
а `src/lib/seoIndexing.ts` не выделяет такой вариант.

Клиентская очистка URL существует. `stripPaymentQuery` вызывается только после
сохранения invoice и session-баннера; это нужно для восстановления покупки,
но не гарантирует очистку до первого обращения Метрики. В `init` счётчика
не была задана отдельно очищенная версия URL. Это подтверждало отсутствие такой
гарантии в просмотренном коде; конкретная последовательность сетевых событий
в этом дополнении не воспроизводилась.

Требования к отдельному исправлению (локально выполнены, production-проверка ожидается):

1. Для RU/EN возвратов с `Shp_*`, `InvId`/`invid`, `SignatureValue`, `payment`
   и другими фактически используемыми платёжными параметрами выдавать noindex
   в первоначальном серверном ответе. Чистая витрина `/coins` остаётся индексируемой,
   canonical указывает на чистую страницу.
2. Обеспечить, чтобы первый просмотр и последующие обращения аналитики не передавали
   платёжные подписи, внутренние user ID и токены. Проверить также URL/referrer
   на страницах сброса пароля и подтверждения email; noindex не очищает аналитику.
3. Сохранить invoice, pending → webhook → confirmed, session-баннер, reload и
   дедупликацию целей. Невозможность записи storage не должна вновь ломать покупку.
4. После исправления проверить публичный HTML/заголовки RU/EN и первый запрос
   тестового счётчика при возврате. Только canonical недостаточно для приёмки.

Отчёт не доказывает возможность начислить VC по найденной подписи или доступ
к чужой переписке. Подпись проведённого платежа не называется новым API-ключом.
Задача — предотвратить публикацию служебных идентификаторов и повторное обнаружение.

## RET-01 Что подтверждено и что требует измерения

Разбор показывает существующую память, а не её отсутствие:
summary, core, эпизоды, RAG и авторская память карточки подключены.
Гостю доступно окно недавних сообщений; RAG имеет ограничения по платному плану.

Наиболее существенные проблемы:

- `Message.chatId` равен ID персонажа, память хранится на паре user+character:
  независимые истории с тем же персонажем не изолированы.
- `prepareFastContext` отбирает память с `intent: general` до результата анализа:
  сюжетный ход получает максимум три кандидата эпизодов вместо десяти.
- RAG выбирает только сообщения `role=user`, хотя важные факты мира и обещания
  персонажа могут появляться в ответах ассистента.
- Основной handler вызывает поиск только при `shouldWaitForRag(fact/question)`;
  условие большой длины истории не помогает обычному сюжетному ходу без поиска.
- Core — один перезаписываемый блок; эпизоды добавляются без статусов замещения
  и отмены. Отбор/подача по важности не гарантирует хронологию.
- Merge старой выжимки с новой главой может переносить ошибки дальше.
- Фоновая память может отставать; при удалении/перегенерации нет доказанного
  точного отката фактов по сообщению-источнику. `MemoryEntry` пишется без чтения.

Два уточнения при сверке с кодом:

1. Финальная сборка `assemblePreparedChatMessages(fastContext, intent, …)`
   **уже происходит после** анализа намерения. Исправлять нужно ранний отбор
   кандидатов и проверять итоговый бюджет, а не считать всю финальную обрезку
   выполняемой с `general`.
2. `getRelevantMemories` **уже вызывает** `sanitizeCoreMemory` при чтении.
   Эта функция чистит структуру, пустые разделы и некоторые строки отношений;
   она не является отдельной защитой от инструкций. Ручной setter сохраняет
   только `trim()` текста. Нужны согласованная запись/чтение, оформление памяти
   как данных и сценарий инъекции; полное отсутствие любой очистки не утверждается.

По отчёту `verify-memory-semantic.cjs` даёт 33/33, но fallback без embeddings
оставляет 55 строк вместо 9. `verify-summary-postprocess.cjs` пишет PASS при
неслитых перефразировках и бытовом событии в важных событиях. Это наблюдения
вывода скриптов, а не измеренный процент забывания реальной моделью.

## RET-01 Этапы оставшейся реализации

### Этап 0 Исправления текущего пути без миграции

Статус с ревью 09.10: реализация завершена после продолжения работы Cursor; дополнительно исправлена воспроизведённая SQL-гонка embeddings. На одном наборе сценариев исходный коммит даёт 8 passed / 20 failed, текущий код — 28 passed / 0 failed; ещё 51 детерминированная проверка. Намеренно возвращённые дефекты хвоста и фоновой записи обнаруживаются. TypeScript, lint файлов этапа и синтетическая сборка прошли. Production-приёмка и проверка настоящей модели ещё не выполнены. [Изменения, доказательства и ограничения](memory-stage-0-implementation-2026-10-08.md).

Исходное задание первого этапа:

Отбирать кандидатов с запасом до intent, выбирать и ограничивать их после;
искать по обеим ролям и по реальной длине истории с сохранением ограничений
плана; после отбора подавать эпизоды в хронологии. Необработанный хвост должен
попадать в контекст до подтверждённого обновления памяти. Для миров учитывать
ответ ассистента. Унифицировать обработку ручной памяти, границу «данные/инструкции»
и убрать ложный PASS существующих скриптов.

Приёмка: сценарный baseline на текущей версии и повтор того же набора после
исправлений; история >3000 токенов без вопроса, факт из ответа персонажа,
изменение имени, хронология, сбой embeddings, задержка фонового обновления,
инструкция в ручной памяти. Тесты должны падать при намеренно возвращённом дефекте.
Контрольные вопросы не содержат правильный ответ. Проверки с заглушками не
выдаются за оценку ответов настоящей модели; небольшая live-выборка — отдельный этап.
Измерять стоимость через AiCostEvent, задержку и полноту памяти совместно.

### Этап 1 Изоляция историй

ChatThread, история по умолчанию для прежних пар, threadId во всех запросах
сообщений/памяти/persona. Аддитивный переход с сохранением старого диалога.
До миграции нужны проверенная исходная схема, baseline миграций и восстановление
бэкапа в отдельной БД. Приёмка: история A не влияет на B, чужой thread недоступен.

### Этап 2 Факты и фоновые задачи

MemoryFact со слотами, active/superseded/retracted, источником; одно извлечение
из полного хода user+assistant вместо независимых переписываний. MemoryJob,
водяной знак, идемпотентность и наблюдаемые failed/retry. Приёмка: новое имя
замещает прежнее, повтор задачи не создаёт дубль, неопределённость не становится фактом.

### Этап 3 События и выжимки

StoryEvent с seq и статусами обещаний/целей; версии ThreadSummary и периодическая
пересборка из подтверждённых фактов/событий. Источники позволяют откатить запись
из удалённого либо отброшенного ответа. Приёмка: порядок событий, закрытие обещания,
перегенерация и отсутствие дрейфа на том же наборе сценариев.

### Этап 4 Интерфейс историй и память миров

Продолжение/новая история/архив, persona на историю и явное согласие на общий профиль.
Для карточек-миров: Character.kind, сущности с алиасами, достоверность утверждений,
отношения NPC, knownBy, состояние сцены и лор автора. Подготовку сущностей можно
начать на этапе 2, сцену/отношения — на этапе 3; полный мир не является условием
выпуска этапа 0. Около 20 из 116 карточек описаны в исходном отчёте как миры/ансамбли;
это выборка того исследования, не свежий пересчёт каталога.

Приёмка для мира: один NPC под разными именами, ложь NPC отдельно от факта,
тайна не известна отсутствующему NPC, смерть/развилка канона, отношения между NPC,
место и время сцены, отсутствие переноса биографии игрока в другую историю.
Модель v2 — предложение, не внедрённая схема и не измеренное улучшение.

## Что зависит от решений владельца

В исходном отчёте остаются вопросы о памяти бесплатного плана, общем профиле,
редактировании запомненных фактов, допустимом отставании/бюджете, сроках хранения,
типе карточки «мир», редакторе лора и журнале NPC/обещаний/тайн.
Эти решения не приняты автоматически при переносе отчёта в аудит.
Оценки $0,00045/$0,0007 фонового вызова из проекта v2 не являются фактическими
расходами нового механизма: он ещё не реализован.

## Ручные действия из отчёта

- 9 октября отправить оставшиеся 24 карточки на переобход, если лимит кабинета
  освободился и они ещё не отправлены. Здесь переобход не выполнялся.
- После проверки noindex воспользоваться удалением из поиска для 21 приватного/
  служебного URL и двух возвратов из оплаты. Ссылки с токенами/подписями не
  публиковать и не отправлять в массовый переобход.
- Проверить источник `/preload`; прямого упоминания этого пути в просмотренном
  `src` не найдено. Это не доказывает отсутствие ссылки в данных/внешних страницах.
  Не создавать индексируемую заглушку ради исчезновения одного 404.
- Обсудить целесообразность обхода по счётчику Метрики; настройка автоматически
  не менялась. Проверить политику служебных URL независимо от этого решения.
- Сравнить новый экспорт 15–22 октября со снимком 8 октября: канонические карточки,
  доля рекламных URL, приватные URL и завершение очереди. Снижение числа всех
  исключений само по себе не критерий: ожидаемый noindex должен сохраняться.
- До этапов памяти со схемными изменениями проверить восстановление production
  backup в отдельную БД и миграционный baseline. Создание бэкапа уже подтверждено
  владельцем; восстановление пока не подтверждено.
