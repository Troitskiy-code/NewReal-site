## Смысл стоимости

- `chat_completions`: `usage.cost` сохраняется в `providerCostNative` с валютой USD
  и семантикой `gateway_total_usd`. Документация caching описывает его как итоговую
  сумму с наценкой и скидкой кэша. Если задан положительный `AI_COST_USD_RUB`,
  пересчёт `usage.cost × курс` даёт **оценку** `chat_usd_estimate`; дополнительных
  10% нет. Без ручного курса используется проверенный свежий курс ЦБ из общего
  кеша (`chat_cbr_estimate`). Ни один из них не объявляется фактическим курсом шлюза.
- Это относится и к служебным запросам к Chat Completions: intent, память,
  summary, события и промпты персонажей.
- `embeddings`: исходный cost сохраняется, но его валюта и включённость наценки
  остаются `null` / `unverified`. Оценка — входные токены × итоговая RUB/1M цена
  каталога. Выходных токенов нет. Курс чата на этот путь не влияет.
- При отсутствии курса чат тоже использует RUB каталог. Порядок ставок:
  `AI_COST_RATES_RUB_JSON`, пригодное поле Model, публичный снимок 8 октября
  `src/lib/data/kodik-cost-rates-2026-10-08.json` (19 моделей). При отсутствии ставки
  стоимость неизвестна. Нулевой native cost сохраняется для сверки и не означает
  бесплатный вызов.
- `cached_tokens` / `cache_write_tokens` — части входных токенов, не прибавляются
  к prompt_tokens. Они сохраняются раздельно. Каталожная оценка не учитывает скидку
  чтения кэша; при ненулевых cache-write без известной ставки оценка по каталогу
  отсутствует, так как запись может быть дороже обычного входа.
- Пересчёт/каталог не записываются в `reportedCostRub`. Старые значения этого поля
  сохраняются без изменения, но выводятся как `legacyUnverifiedRub`, а не как
  подтверждённые списания.

## Реализация рублёвых оценок и импорта

Существующий cron `/api/cron/update-currency` сохраняет источник `cbr`, дату курса
из XML ЦБ и время загрузки. Условные 90/100 RUB остаются только для отображения.
Для учёта проверяется источник, возраст загрузки менее 24 часов, допустимая дата
курса (не старше 10 дней с учётом выходных), отсутствие будущего времени загрузки.
Старые файлы кеша без источника, stale и fallback для учёта не принимаются.
Параллельные обновления используют один HTTP-запрос. Cron возвращает 503 при
отсутствии пригодного курса вместо ложного `ok=true`. Сборщик чата только читает
кеш и не ждёт HTTP ЦБ; до первого обновления применяются каталожные оценки.

Ставки снимка получены из листа «Цены моделей» проверенной выгрузки Cursor.
Это вход/выход RUB за 1M токенов, без подгонки Gemma/DeepSeek под двухмесячную
историю. У embeddings вход 1,95 RUB, выход 0. Список алиасов содержит только
`text-embedding-3-small` → `openai/text-embedding-3-small`; он общий для выбора
ставки и сверки модели. Произвольное удаление префикса провайдера не применяется.
Снимок датирован и не обновляет цены автоматически; при изменении тарифов нужно
обновить каталог Model, явные ставки или снимок. Скидка чтения кеша по-прежнему
не применяется к резервной оценке, а cache-write без доказанного тарифа остаётся
unknown; преимущество имеет полученный chat USD-cost с пригодным курсом.

`scripts/lib/kodik-cost-export.mjs` принимает исходный CSV с разделителем `;`,
BOM/CRLF/кавычками и десятичной запятой, а также JSON. Суммы нормализуются через
целые десятичные единицы без Number-округления; токены проверяются как целые.
Дата без смещения требует явного подтверждения UTC, некорректные даты/суммы/
колонки приводят к отказу всего импорта. Исходные файлы не изменяются. Имя ключа
обязательно в каждой строке; секреты, промпты и произвольные поля не переносятся.

`npm run economy:import-kodik -- --input <CSV> --output <JSON> --naive-timezone UTC`
создаёт нормализованный JSON вне репозитория, без перезаписи существующего файла.
Реальный CSV успешно импортирован: 91501 строк, `costRubExact=2309.37519`,
единственный ключ `NewReal Chat`. Raw CSV/JSON с ID запросов не включаются в Git.
Это проверка импорта; совпадение каждой строки с production AiCostEvent отдельно
этой проверкой не подтверждено.

Отчёт читает CSV непосредственно либо нормализованный JSON. Для исходного CSV
задать `KODIK_COST_EXPORT_TIMEZONE=UTC`; JSON с явными смещениями этого не требует.
Параметры дат и SQL-сессия используют UTC независимо от часового пояса машины.
Сверка сохраняет проверки уникальности ID и токенов, допускает только проверенный
embedding-алиас. Оценка заменяется найденным RUB-списанием, не складывается с ним;
БД и старые события не изменяются. Отношения 95,45 и 97,26 не используются как FX.

Официальные источники:

- [Чат, кэш и стоимость](https://kodikrouter.ru/docs/caching).
- [Итоговые цены каталога и наценка](https://kodikrouter.ru/pricing).
- [Заголовок шлюза](https://kodikrouter.ru/docs/gateway).
- [ID тела ответа провайдера](https://kodikrouter.ru/docs/examples).

Формулировка caching об «авторитетной стоимости провайдера» неоднозначна рядом
с определением итоговой стоимости чата. Для финальных расходов используется
рублёвая выписка; семантика rerank/Decisions не применяется ко всем endpoint.
Пути `cost_rub` / `cost_usd` в API-ответе не установлены и не угадываются парсером.

## Сверка без записи в БД

`npm run economy:costs` формирует JSON `schemaVersion: 2`. Соединение берётся
только из явно заданного `COST_REPORT_DATABASE_URL`, `.env` не загружается.
Транзакция READ ONLY, timeout 30 секунд; до 200000 событий за отчёт.
Период: `COST_REPORT_DAYS` (14 по умолчанию) или `COST_REPORT_FROM` /
`COST_REPORT_TO` в ISO с явным Z/смещением. Слишком большой период/число строк
отклоняются вместо неполного отчёта.

Для сверки дополнительно указать:

- `KODIK_COST_EXPORT`: путь к CSV или JSON истории KodikRouter вне Git;
- `KODIK_COST_API_KEY_NAME`: точное имя ключа в экспорте, например `NewReal Chat`
  (это имя, не секрет);
- `KODIK_COST_EXPORT_TIMEZONE=UTC`: только для подтверждённого UTC без смещения;
- `COST_REPORT_OUTPUT`: путь для агрегированного отчёта, если нужен файл.

Сопоставление только по точному совпадению экспортного `request_id` с отдельно
сохранёнными `providerRequestId` (заголовок шлюза) или `providerResponseId`
(JSON/SSE id). Проверяются фактическая модель и имеющиеся измеренные токены.
Совпадение времени/токенов без ID не подтверждает связь. Исторические response ID
не выдумываются. Если ID повторяется у разных событий/строк либо два ID указывают
на разные списания, расход остаётся несопоставленным.

Повтор одной и той же строки выписки с тем же ledger id не удваивает расход.
Проверка уникальности ID запроса учитывает также строки с нулевой/отсутствующей
суммой и статусом ошибки. Они не могут скрыть неоднозначность другой строки.
Чужое имя ключа, отрицательная/невалидная стоимость и несоответствие модели
не подтверждаются. Нулевые/отсутствующие суммы показываются отдельно; не
объявляются бесплатными. Суммирование рублёвой выписки — десятичное,
`confirmedCostRubExact` сохраняет точную строковую сумму.

Подтверждённая экспортом RUB сумма заменяет оценку того же события в отчёте,
не складывается с ней. Сам журнал БД не изменяется. `reportedCostRub` в JSON v2
— совместимый псевдоним **подтверждённого** итога, не старого поля БД.
Всегда раздельны confirmed / estimated / unknown и исключённые legacy суммы.

Итоги всего экспортного файла могут охватывать другой период, чем AiCostEvent.
Часовой пояс экспорта без смещения не угадывается; общий `exportSuccessRub`
не подставляется вместо стоимости событий в периоде. Из отчёта исключены
пользователи, emails, диалоги, секреты и исходные строки экспорта.

## Экономический калькулятор

`ECONOMY_COST_REPORT` принимает только JSON v2. Средний сценарий использует
затраты и реально списанные VC по тем же покрытым платным чатам. Гостевые и
нулевые VC-вызовы учитываются в общей себестоимости отчёта, но исключаются
из платной цены запроса. Требуется ≥90% покрытия usage и стоимости для каждой
платной модели. Этот порог не доказывает достаточность выборки или прибыль.

Low/high/stress — прогнозы по p50/p95 и каталогу, а не суммы выписки.
В среднем сценарии оценки также могут присутствовать; разделение подтверждений
и оценок сохраняется в metadata. Retry/RAG, CAC, налог, возвраты и инфраструктура
остаются предположениями. Отчёт не объявляет измеренной маржой все расходы сайта.

## Выкладка

Штатно применять **до кода** миграцию `20261008160000_ai_cost_accounting_v2`
после проверки истории Prisma. Для уже выложенного кода и базы без истории
подготовлено точечное применение через Adminer, описанное выше. Она добавляет
второй ID, endpoint, версию/семантику учёта,
cache-write и индексы. Существующие строки сохраняют `accountingVersion=1`;
новые строки явно записывают 2. История и ранее начисленные VC не изменяются.
Runtime роль не должна получать DDL. Сборщик при сбое записи не ломает AI-ответ,
но полноту сбора после релиза нужно проверить отдельно.

`KODIKROUTER_USAGE_COST_CURRENCY` больше не читается: общая настройка не может
задавать семантику разных endpoint. Обязательных новых runtime переменных нет.
`AI_COST_USD_RUB` опционален для чатовой оценки; без него используется свежий
проверенный курс ЦБ из кеша, затем RUB каталог при отсутствии пригодного курса.
Не подставлять условный курс или сегодняшний курс для исторического списания.
Новых cron нет. Production-схема, запись событий и рублёвые оценки чата/intent
проверены выше; расчёт embeddings в production, сверка и длительное покрытие
остаются отдельными проверками.

Для новой реализации дополнительной миграции нет. При последующих выкладках нужно дождаться
существующего currency cron либо один раз вызвать его для обновления кеша с
источником/датой, затем проверить новые рублёвые оценки на живом запросе.

Для внешней production-БД нужен отдельный запуск миграции вне сборки Relaxdev.
Prisma CLI здесь использует `DATABASE_URL` из datasource, не `DIRECT_URL`;
`npm run db:preflight` требует явный `MIGRATION_DATABASE_URL` и не читает `.env`.
Обе переменные при работе оператора должны указывать на одну проверенную
production-БД с миграционной ролью. Значения подключения не включать в отчёт.

Перед записью проверить резервную копию, фактическую схему и историю
`_prisma_migrations`. `prisma migrate deploy` применяет все pending миграции,
а не только v2. Если истории нет или ранее таблицы создавались через db push,
сначала сверить baseline по инструкции `docs/p1-operational-release.md`;
не исполнять baseline SQL поверх существующих таблиц и не помечать всю историю
applied без проверки. При проверенной истории применить pending миграции
штатным порядком, затем проверить пять колонок, два индекса, историю и появление
новых AiCostEvent с accountingVersion=2. Одного отсутствия свежих ошибок без
AI-запросов недостаточно для приёмки. При исправлении только этой схемы перезапуск
приложения обычно не требуется: production Prisma Client уже собран под v2.
