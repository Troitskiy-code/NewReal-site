# DATA-01: атрибуция подтверждённых оплат

Статус: реализация в рабочей копии; production-миграция DATA-01 применена **09.10.2026, 18:27 МСК**, состав схемы и runtime-права проверены. Выкладка кода, сверка следующей реальной покупки с живой Метрикой и историческая проверка UTC ещё не выполнены. Коммит/push не выполнялись. Код памяти, себестоимость, цены, рекламная стратегия и бюджет этой задачей не менялись.

## Что реализовано

1. `CheckoutAttributionCapture` в AppShell сохраняет первый визит и последний непрямой источник в пределах 30 дней. Перед нажатием оплаты обе формы получают снимок: безопасные UTM, числовой yclid, hostname внешнего referrer, при готовом счётчике — его clientID. Ожидание callback `getClientID` ограничено 800 мс. Недоступная Метрика не блокирует оплату.
2. Новый `PaymentOrder` записывается сервером до выдачи формы Robokassa: provider/invoiceId, внутренний владелец, серверные пакет/тариф/сумма, период, снимок источника, признак теста. Источник не отправляется в Shp/Robokassa и не логируется. Повтор первого пакета использует прежний invoice и неизменный снимок; регистрация источника и резерв первого пакета выполняются в одной транзакции. Обычный checkout при коллизии invoice завершается ошибкой, а не подменяет источник существующего заказа.
3. Истиной об оплате остаётся уникальный `PaymentEvent`, создаваемый подписанным webhook вместе с начислением. Webhook и начисления не изменены. Созданный checkout сам по себе не является продажей.
4. `/api/payment/status` выдаёт владельцу `orderId` вида `po_<случайный id>` только после подтверждения. Исторические оплаты без нового заказа получают устойчивый `pe_<id события>`; история источников не выдумывается. Связь заказа с событием требует совпадения provider/invoice, владельца, типа, тарифа и суммы. Чужой/неподтверждённый invoice не раскрывает метаданные заказа.
5. Этот `order_id` добавлен в существующие цели VC, подписки и тарифа. Сумма и RUB остаются только на основной цели покупки. В параметры целей не добавляются invoice, userId, clientID, yclid, email или URL. Продления и объявленные сервером тесты не отправляют цели новых покупок. Серверная/офлайн-отправка целей не добавлена.
6. Новый `/api/payment/analytics` принимает отдельно клиентские статусы попытки и callback. Сессия, доверенный Origin, принадлежность PaymentEvent, orderId, допустимая цель и лимит attempts проверяются сервером. `PaymentGoalReceipt` уникален по eventId/goal; атомарный upsert сохраняет максимальный счётчик попыток и терминальный `callback_completed`. Запоздалый timeout его не стирает. Ошибка отправки receipt не вызывает повторный reachGoal и не влияет на оплату.
7. `payments:attribution` строит read-only отчёт по подтверждённым событиям: первые покупатели за всю известную историю PaymentEvent, повторные оплаты, продления, тесты, источники/кампании, отсутствие аналитических отметок. Отсутствие цели не обнуляет выручку. Подтверждённая сумма — валовая RUB до комиссий/налогов, не прибыль. Неизвестная историческая сумма учитывается отдельным счётчиком.

## Границы и приватность

- UTM/yclid/clientID — сообщения браузера об источнике, не доказательство атрибуции Яндекса. Модель отчёта явно названа: first touch / last non-direct, окно 30 дней. Метрика/Директ могут относить конверсию к другому визиту и периоду; сравнивать надо одинаковые периоды и выбранную модель их отчёта.
- Используются sessionStorage и память вкладки. Источник переживает reload и гостевой вход в той же вкладке. Выход/смена аккаунта очищают его; поздний SDK callback ограждён поколением/владельцем. Новая вкладка, новое устройство и закрытая вкладка не гарантируют перенос источника. Без хранилища возможен только текущий документ; это не заявление о сквозной атрибуции на 30 дней.
- URL возврата и страницы email/reset токенов не обновляют источник. Referrer хранится только hostname; собственный сайт, Google OAuth и Robokassa не становятся новым источником. Из клиентских объектов сервер принимает только ограниченный список полей/длин/форматов; counter/clientID принимаются парой только для настроенного счётчика.
- Поступивший `callback_completed` доказывает лишь сообщение клиента о callback SDK. В каждом заказе `metrikaDelivery: unverified`: фактическая доставка/атрибуция подтверждается отдельно в кабинете. Все browser receipt ненадёжны по определению и не используются для финансового начисления. Потерянный receipt остаётся `not_reported`, а не «платежа не было».
- Межвкладочное exactly-once при полном отказе storage по-прежнему не гарантируется. Существующие ограничения повторов целей сохранены. Нельзя включать параллельно серверную доставку без согласованной дедупликации.
- Исторические тесты владельца исключаются только по явно заданному списку его account ID. По сумме/дате/частоте нельзя самостоятельно объявлять пользователя тестом. `real` в JSON означает «не объявлено тестом», это уточнено в `classificationRule`.
- Возвраты неизвестны без отдельного реестра оператора. Отменённая попытка оплаты не является возвратом или второй продажей.

## Read-only отчёт

Команда `npm run payments:attribution` никогда не читает `.env` и не отправляет цели. Необходимы явные переменные процесса:

- `PAYMENT_REPORT_DATABASE_URL`: соединение с проверяемой БД; предпочтительна отдельная роль только для чтения.
- `PAYMENT_REPORT_FROM`, `PAYMENT_REPORT_TO`: ISO UTC с `Z`, интервал `[from, to)`, максимум 366 дней. Например `2026-10-09T00:00:00Z` и `2026-10-10T00:00:00Z`.
- `PAYMENT_TEST_USER_IDS`: тот же список account ID тестового владельца, если нужны исключения исторических покупок.
- Опционально `PAYMENT_REFUNDS_FILE`: полный для выбранных заказов операторский JSON-реестр с `id`, `orderId`, числовым `amountRub`, `refundedAt` в UTC с `Z`. Проверяются уникальность refund id, наличие заказа, положительная сумма, время после оплаты и предел суммы заказа. Это структурная проверка ввода, не обращение к Robokassa и не подтверждение полноты реестра. Возвраты относятся к выбранным заказам и могут происходить после конца периода оплат.

В транзакции проверяется `transaction_read_only=on`, ограничивается время запросов. Объём свыше 100 000 оплат прерывает отчёт вместо тихого обрезания. Даты `timestamp without time zone` трактуются как UTC согласно соглашению приложения; SQL явно приводит параметры и выдачу к UTC, без зависимости от часового пояса компьютера. До production-приёмки проверить TimeZone БД и сопоставить `PaymentEvent.createdAt` с известной оплатой; исторический сдвиг времени эта задача автоматически не исправляет.

Агрегаты печатаются в консоль. Детальный JSON с orderId ↔ invoiceId сохраняется в отдельный системный временный каталог вне Git; сырые userId/clientID/yclid/email не экспортируются. Для сверки конкретного заказа в Метрике используется `order_id`, а для Robokassa — invoiceId из этого приватного отчёта. ClientID хранится только в серверном снимке для адресной сверки визита уполномоченным оператором; публичного API для выгрузки этих идентификаторов нет.
