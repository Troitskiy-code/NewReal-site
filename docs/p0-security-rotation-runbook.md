# Runbook: production-ротация NEXTAUTH_SECRET и пароля БД

Этот документ для владельца/оператора RelaxDev (NewVerse). **Не выполнять из агента.** Не вставляйте значения секретов в чаты, тикеты, логи и этот файл.

Ротация **отзывает** раскрытые credentials: старый `NEXTAUTH_SECRET` перестаёт принимать JWT, старый пароль БД отвергается на новом соединении. Ротация **не удаляет** исторические копии тех значений в git history, старых логах, бэкапах и тикетах. Перепись git history — отдельное решение владельца, здесь не описывается как обязательный шаг.

Возможность окна обслуживания, staging-слотов и точный UX панели хостинга из репозитория **подтвердить нельзя**; оператор сверяет это в панели RelaxDev перед выполнением.

## 1. Потребители и где менять конфигурацию

Секреты живут в панели RelaxDev (environment / secrets приложения), не только в локальном `.env`.

| Переменная | Кто читает | Где используется |
| --- | --- | --- |
| `NEXTAUTH_SECRET` | Next.js runtime (все инстансы `next start` / RelaxDev app) | `src/lib/auth.ts` — подпись JWT-сессий NextAuth. Обязательна через `getRequiredEnv`. |
| `DATABASE_URL` | Тот же app runtime; PrismaClient singleton; Prisma CLI | `src/lib/prisma.js` и `prisma/schema.prisma` (`datasource.url = env("DATABASE_URL")`). Обязательна. В production должны быть `connection_limit` и `pool_timeout` (см. `.env.example`). |
| `DIRECT_URL` | Только явные служебные скрипты, не Prisma CLI | В текущем репозитории **нет** `directUrl` в `prisma/schema.prisma` и нет `prisma.config.ts`. Само наличие `DIRECT_URL` в панели **не** переключает `prisma migrate` / Prisma CLI. Фактические читатели: `scripts/translate-characters.ts`, `scripts/compress-avatars.ts`, `scripts/backfill-character-slugs.ts` (берут `DIRECT_URL` или fallback на `DATABASE_URL`). `src/app/api/app-instances/export/route.js` только перечисляет имя переменной при экспорте env, это не runtime-консьюмер БД. |

Служебные команды на том же приложении, которым нужна живая БД после смены пароля:

- `next start` / процесс RelaxDev (читает `DATABASE_URL`);
- разовые `npx prisma migrate deploy` / `prisma generate` — в этой кодовой базе идут в `DATABASE_URL`, не в `DIRECT_URL`;
- перечисленные скрипты (`translate-characters`, `compress-avatars`, `backfill-character-slugs`), если оператор запускает их против production: обновить и `DIRECT_URL`, и `DATABASE_URL`;
- cron HTTP-вызовы на это же приложение: `/api/cron/renew-subscriptions`, `/api/cron/update-currency`, `/api/cron/cleanup-notifications`, `/api/cron/cleanup-anonymous`, `/api/cron/deliver-support` — отдельного worker-процесса нет, они ходят в ту же БД через тот же runtime и `DATABASE_URL`.

Отдельного очереди/worker-хоста в репозитории нет. Если в панели есть preview/staging инстансы с копией тех же переменных — обновить каждый потребитель.

`TEST_DATABASE_URL` — только изолированные проверки, не production.

## 2. Новые значения

1. **NEXTAUTH_SECRET:** сгенерировать криптографически стойкую случайную строку (например `openssl rand -base64 48` на доверенной машине оператора). Сохранить только в секретах панели. После смены **все существующие JWT-сессии становятся недействительными**; пользователи входят заново. Это ожидаемо.
2. **Пароль БД:** создать новый пароль той же стойкости в консоли PostgreSQL-провайдера RelaxDev / хостера БД. Не менять имя БД, схему, роли приложения и данные ради ротации.
3. Не записывать новые значения в git, скриншоты панели и общие каналы.

## 3. Порядок смены (окно разрыва соединений неизбежно)

Бесшовной ротации пароля БД эта платформа не обещает: старые пулы держат прежний пароль, новые подключения со старым паролем отвергаются, как только провайдер его меняет.

Рекомендуемый порядок:

1. Подготовить новые значения в секретах панели. Есть ли короткое окно обслуживания / staging-слот — уточнить у оператора панели; из репозитория это не видно.
2. Если панель позволяет: короткое окно, не принимать трафик приложения.
3. Сменить пароль пользователя БД на стороне PostgreSQL.
4. Сразу обновить `DATABASE_URL` в **каждом** инстансе приложения. URL целиком, не «дописать пароль в чат». Если оператор реально запускает скрипты, которые читают `DIRECT_URL`, обновить и её тем же паролем. Prisma CLI в этой кодовой базе `DIRECT_URL` сам не подхватит.
5. Обновить `NEXTAUTH_SECRET` в тех же инстансах.
6. Перезапустить все потребители (app + любые ручные Prisma-команды и скрипты из таблицы выше). Не оставлять старый процесс с прежним env.
7. Не возвращать раскрытый `NEXTAUTH_SECRET` «на всякий случай» и не держать два валидных auth-секрета.

Пока шаг 4 не дошёл до всех процессов, часть инстансов будет получать отказ в подключении — это ожидаемое окно, не баг бесшовности.

## 4. Проверки после смены (только статус, без значений)

Оператор выполняет и записывает pass/fail:

| Проверка | Ожидание |
| --- | --- |
| Новый логин (credentials и Google, если включён) | Сессия создаётся |
| Старый JWT / старая cookie сессии | Отклоняется, нужен повторный вход |
| Подключение клиентом со **старым** паролем БД | Отказ аутентификации |
| Приложение с новым `DATABASE_URL` | Страницы и cron, которым нужна БД, отвечают без ошибки пула |
| Новые логи приложения (console / Logtail) | Нет connection string, Bearer, паролей, полных email в auth/cron/payment ошибках |

Не вставлять URL, пароли и токены в отчёт проверки.

## 5. Сбой и восстановление

- Если приложение не стартует: проверить, что **новые** `DATABASE_URL` / `NEXTAUTH_SECRET` заданы на всех инстансах и процесс перезапущен. Не откатывать на раскрытый секрет.
- Если БД отвергает пароль: сверить, что пароль в панели совпадает с паролем роли в PostgreSQL; исправить только новым значением.
- Если пользователи «вылетели»: это следствие смены `NEXTAUTH_SECRET`; восстановление — повторный вход, не возврат старого секрета.
- Ранее опубликованные логи и git history ротация **не удаляет**; нужен отдельный план, если требуется стереть исторические копии.
