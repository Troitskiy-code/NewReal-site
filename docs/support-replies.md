# Ответы поддержки через Resend

Администратор открывает `/ru/admin/support`, вводит существующий ADMIN_SECRET (только память вкладки), выбирает тикет и сохраняет ответ. API требует Bearer авторизацию даже для чтения. Получатель берётся исключительно из тикета. Текст отправляется без HTML, секреты, текст обращения и email не логируются.

SupportReply хранит ответ, фиксированные sender/recipient, уникальный clientKey, хеш содержимого, состояние и идентификатор Resend. Повтор запроса с тем же ключом не создаёт второе письмо; другое содержимое возвращает 409. Cron deliver-support обрабатывает одну исходную заявку и один ответ за запуск. Повторные попытки ограничены шестью и 23 часами; используется стабильный ключ Resend и claim с fencing. Dead требует ручного разбора, автоматического повторного начисления/отправки за пределами окна нет.

`accepted` означает принятие Resend, а не доказанную доставку. Delivery webhook и входящая почта не реализованы. Письмо предлагает продолжить через форму поддержки с номером тикета; новое обращение автоматически не объединяется со старым.

## Открытие тикета при неприменённой миграции

При исходном запросе с `include: replies` отсутствие SupportReply (Prisma P2021) или её колонки (P2022) мешало загрузить даже исходное обращение. Теперь исходный тикет и история ответов читаются отдельно. Текст обращения доступен; панель показывает необходимость применить `20261006120000_support_replies` и блокирует отправку. Прямой POST также возвращает 503 с кодом `SUPPORT_SCHEMA_NOT_READY`. После миграции достаточно обновить статус ответа. Неизвестная ошибка истории имеет отдельное сообщение, не выдаётся за отсутствие миграции; сервер пишет только безопасную диагностику без email/текста/секретов.

Регрессионная проверка использует старую схему настоящего изолированного PostgreSQL до применения SQL, затем схему с отсутствующей колонкой и восстановленную схему. Браузер проверяет видимость исходного обращения, предупреждение, запрет отправки и восстановление после обновления. Рабочую БД проверять из этой среды не удалось (EACCES); наличие этой проблемы на сервере требует подтверждения логами/статусом миграции. Обычный build выполняет prisma generate и не применяет миграции.

## Проверка и применение без консоли Relaxdev

В панели `/ru/admin/support` есть «Проверить миграцию». Авторизованный GET `/api/admin/support/migration` только читает структуру SupportReply, индексы/ключи/значения по умолчанию, запись в `_prisma_migrations` и права подключения. Если это возможно, панель показывает отдельную кнопку применения с явным подтверждением. POST принимает только `{ "action": "apply", "migration": "20261006120000_support_replies" }`, выполняет фиксированный SQL из этой миграции и записывает её checksum в существующую историю Prisma. Если совместимая таблица уже создана, выполняется только запись в историю. Повторное применение — безопасный no-op.

Обе операции требуют ADMIN_SECRET в Bearer-заголовке. GET не меняет БД. Для POST проверяется Origin; ключ нельзя передавать в URL. SQL, путь или название произвольной миграции не принимаются. Транзакция и advisory lock защищают от параллельного применения; при сбое изменения откатываются. SQL-файл явно включён в серверный trace сборки Next.js.

Уточнение для БД без истории миграций (скриншот владельца, 2026-10-06): при отсутствии `_prisma_migrations` включается `mode: schema_only`. Панель показывает «Создать таблицу ответов» с отдельным подтверждением. В этом режиме выполняется только фиксированный SQL создания SupportReply, её ключей и индексов. История Prisma не создаётся, предыдущие миграции не помечаются выполненными. После установки `ready: true`, `history: missing`, `canApply: false`; ответы пользователям доступны, повторное применение ничего не меняет. Описанная выше запись checksum относится только к режиму `prisma`, когда история уже существует с подтверждённым baseline. Для будущего перехода всей существующей базы на Prisma migrate нужна отдельная настройка baseline; установка таблицы ответов её не заменяет.

Дополнительная проверка на частном PostgreSQL воспроизводит отсутствие обеих таблиц в заполненной БД: установка сохраняет тикет, позволяет поставить ответ в очередь и отправить через подставной отправитель, не создаёт историю Prisma и сохраняет ответ при повторном запуске. В обоих режимах проверен реальный откат после ошибки последнего индекса. Браузерные проверки покрывают schema_only и prisma на 390/1280, подтверждение и доступность отправки после установки. На production создание таблицы не выполнялось.

Неполная/несовместимая таблица, запись об уже применённой миграции при отсутствующей таблице, незавершённые миграции или нехватка прав блокируют применение. При существующей истории Prisma без подтверждённого baseline запись в неё также заблокирована. Само отсутствие истории не мешает установить новую таблицу в режиме schema_only. История предыдущих миграций не создаётся и не подделывается. При нехватке прав или несовместимости нужен администратор базы/поддержка Relaxdev; панель сообщает причину. Другие миграции, таблицы и пользовательские обращения не изменяются. В рабочей базе API автоматически не вызывается при загрузке страницы.

Проверки API на частном PostgreSQL прошли: отсутствие авторизации, чужой Origin, запрет произвольного SQL/миграций, отсутствие истории/baseline, роль без DDL, незавершённая миграция, конкурентное применение, реальный откат после ошибки последнего индекса, совпадение checksum, повторное применение и принятие записи последующим `prisma migrate deploy`. Уже готовая таблица с существующим ответом сохраняет данные при записи в историю. Браузер 390/1280 подтверждает, что проверка ничего не применяет, применение требует отметки подтверждения и затем открывает отправку ответа. Финальная сборка с синтетическими настройками, ESLint, P0 security (118), P0/P1 (40) и diff-check прошли. Рабочая миграция не применялась, commit/push не выполнялись.

До запуска создать схему ответов через панель либо применить `20261006120000_support_replies` при использовании Prisma migrate; проверить существующие RESEND_API_KEY, ADMIN_SECRET и cron. Опциональная SUPPORT_FROM_EMAIL: `NewVerse Support <support@newvers.ai>`, это же значение используется по умолчанию. Домен newvers.ai должен быть подтверждён у Resend. Никаких production-писем проверки не отправляют.

Проверено: `node scripts/verify-support-replies.mjs` — настоящая миграция на частном PostgreSQL, реальные API/очередь с подставным отправителем (авторизация, получатель, конкурентные запросы, идемпотентность, retry, истечение окна, защита от cross-site). `node scripts/verify-support-browser.mjs` — Edge 390/1280, открытие тикета, ответ, отсутствие ключа в storage и очистка при выходе. TypeScript, ESLint изменённых файлов, сборка с синтетическими env, P0 security (118), P0/P1 (40) прошли. Сборка имеет прежнее предупреждение трассировки next.config/currencyRates. Production-миграция и реальная доставка ещё не проверены; commit/push не выполнялись.
