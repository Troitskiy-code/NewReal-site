# Независимые истории с одним персонажем (ChatThread): реализация

Дата: 12 октября 2026. Задание: [chat-threads-task-2026-10-12.md](chat-threads-task-2026-10-12.md).
Статус: реализовано и проверено в worktree `claude/zealous-goodall-8b037c`. **Не закоммичено**, production (БД, env, деплой Relaxdev) не трогался, платные AI-провайдеры не вызывались.

## Коротко

- Пользователь ведёт несколько историй с одним персонажем: у каждой свои сообщения, RAG, сводка, core, эпизоды, `MemoryEntry`, персона, закреплённая версия сборки промпта и учёт стоимости.
- Новая сущность `ChatThread`, аддитивная миграция: история по умолчанию для каждой существующей пары, пакетное заполнение `Message.threadId`.
- Флаг `CHAT_THREADS_ENABLED` (по умолчанию выключен). При выключенном флаге поведение прежнее: одна история на пару, API историй отвечает 404, интерфейс историй скрыт. Откат делается флагом, схему откатывать не нужно.
- UI: переключатель и список историй в чате, «Продолжить» и «Новая история» на странице персонажа, строки историй в `/chats`. Тексты RU/EN.
- Проверки: новая `verify:chat-threads` (99), браузерная `verify:chat-threads:browser` (18), весь регрессионный набор из «Приёмки», TypeScript, lint, синтетическая сборка.

## Решения

### По вопросам владельцу (приняты умолчания задания)

1. Лимита числа историй нет. От массового создания пустых записей скриптом стоит защитный rate limit: 30 созданий за 10 минут на пользователя. Это ограничение частоты, а не количества.
2. Удаление необратимо: подтверждение в интерфейсе, а API требует `{ "confirmed": true }`. Архив — обратимая альтернатива.
3. Название автоматическое, «История N» / «Story N» (`ChatThread.number`), его можно переименовать (до 80 символов, управляющие символы вычищаются). Пустое название возвращает автоматическое. После удаления последней истории её номер может использоваться снова.
4. Гости списка историй не видят: у гостя одна история.
5. `chat_engaged` по-прежнему считается один раз на пользователя+персонажа за визит (ключ `actor:characterId` в `acquisitionGoals.ts` не менялся). В Метрику идентификаторы историй не передаются.

### Технические

- **`Message.threadId` — отдельная колонка, а не `chatId`.** У неё FK на `ChatThread` с `ON DELETE CASCADE`: удаление истории каскадом удаляет сообщения, а через них оба хранилища эмбеддингов. Старые значения `chatId` (id персонажа) не путаются с id истории. `chatId` по-прежнему пишется равным `characterId`, чтобы код предыдущей версии продолжал работать.
- **Персона.** Персона истории хранится в `ChatThread.personaId` (`ON DELETE SET NULL`). `PersonaSelection` остаётся «последним выбором для пары», в него пишется одновременно с историей, и из него новая история копирует персону, если выбор сделан не внутри чата. Кнопка «Новая история» в чате копирует персону из открытой истории (`sourceThreadId`).
- **`ChatPromptState`.** Ключ `user:<id>` закреплял версию сборки и режим «этой истории», поэтому для историй ключ стал `thread:<id>`. Миграция копирует старое состояние в историю по умолчанию, строки `user:` сохраняются для отката кода. Новая история начинает с версии и режима из актуальной карточки, как при первом входе.
- **`memoryWatermarkMessageId` не добавлен.** Текущей фоновой памяти он не нужен (покрытие считается по `Memory.lastSummarizedAt`), его время — этап 2.
- **`WorldEvent` пользовательский сюжет не получает.** Запись идёт только через ручной `POST /api/events` владельцем карточки или участника, cron жизненного цикла отключён (`/api/cron/update-characters`), в промпт чата события не читаются. Утечки между историями и пользователями нет, изоляция не требуется.
- **Эмбеддинги.** Денормализованный `threadId` в `MessageEmbedding*` не добавлялся: поиск уже соединяется с `Message`, и фильтр по истории ставится там (индекс `Message(threadId, createdAt)`). Cron дозаполнения эмбеддингов работает по id сообщения и не менялся.
- **Учёт стоимости.** В `AiCostEvent.threadHash` пишется HMAC(`NEXTAUTH_SECRET`, `thread:<id>`), сырой id не сохраняется. Фоновая память того же запроса наследует контекст и пишет тот же хэш. Списание VC и лимиты не менялись.
- **URL.** `/chat/[id]?thread=<id>`. Ключ `thread` добавлен в приватные параметры SEC-04 (`urlPrivacy.ts`): он вырезается из адресов для Метрики, страница получает `Referrer-Policy: no-referrer` и `X-Robots-Tag: noindex`. Страницы чата и так `noindex`. Без параметра открывается последняя активная история. Пустая история создаётся только по кнопке «Новая история» или первым сообщением, простое открытие страницы её не создаёт.
- **«Выбранная история» при возврате** — это последняя по активности (`lastMessageAt`: сообщение или создание истории). Если открыть старую историю и ничего в ней не написать, при возврате без параметра откроется более свежая. Отправка сообщения в архивную историю возвращает её в активные.
- **Гостевой claim.** При включённом флаге гостевые сообщения всегда становятся отдельной новой историей (номером 1, если историй у пользователя ещё нет) с режимом, закреплённым у гостя. При выключенном флаге остаётся прежнее слияние в единственную историю.
- **Режим «флаг выключен»** определён как одна история на пару: последняя по активности плюс строки сообщений, которые пакетное заполнение ещё не обработало (`threadId IS NULL`). Поэтому код можно выкладывать до окончания заполнения, а при откате флагом истории, созданные при включённом флаге, скрыты, но не потеряны. Память всегда читается строго по истории: в миграции она заполняется целиком.

## Миграция

Порядок внутри `migration.sql` (каждый шаг защищён и безопасен при повторном выполнении: `IF NOT EXISTS`, `NOT EXISTS`, `ON CONFLICT DO NOTHING`, проверка `pg_constraint`):

1. Таблица `ChatThread`, nullable-колонки `threadId` и `threadHash`, индексы, FK.
2. Для каждой пары с сообщениями или памятью, у которой ещё нет истории, создаётся история номер 1. `personaId` берётся из `PersonaSelection` пары. `lastMessageAt` равен времени последнего сообщения, а время памяти используется, только если сообщений нет (это расхождение нашла проверка и оно исправлено до финального прогона).
3. `Memory`, `CoreMemory`, `EpisodicMemory`, `MemoryEntry` получают `threadId` истории по умолчанию (одним оператором: таблицы ограничены по размеру на пару).
4. `ChatPromptState`: `user:<id>` копируется в `thread:<id>` истории по умолчанию.
5. Только после заполнения удаляются `Memory_userId_characterId_key` и `CoreMemory_userId_characterId_key` и вместо них создаются обычные индексы.

`Message.threadId` заполняется не миграцией, а `scripts/backfill-chat-threads.mjs`: пачками по 5000 строк (`--batch-size`), каждая пачка — своя короткая транзакция с `FOR UPDATE SKIP LOCKED`. Тот же скрипт подбирает строки, которые старый код записал во время выкладки, создаёт историю для новой пары и сдвигает `lastMessageAt`. Режим `--check` завершается с кодом 1, пока есть хоть одна строка без истории. Скрипт не читает `.env`: адрес задаётся явно через `MIGRATION_DATABASE_URL`.

`threadId` пока nullable: так выкладка остаётся аддитивной, а старый код во время переключения не падает. `NOT NULL` можно ввести отдельной миграцией после стабильной работы с включённым флагом.

- `verify:economy:costs` нестабилен на устаревшей проверке Createya (Createya заменён на Kie AI). К историям не относится: файлы Createya не менялись, на HEAD то же поведение. Проверку стоит удалить вместе с остальной зачисткой Createya.
- Общий lint проекта не запускался, только файлы этой задачи. Две ошибки, существующие до задачи, не исправлялись.
- **Конфликты при слиянии.** В основной рабочей копии есть незакоммиченные изменения других задач в тех же файлах (`api/chat/[id]/route.ts`, `regenerate/route.ts`, `aiCostTelemetry.ts`, `public/locales/*`, `package.json`, `verify-guest-p1.mjs`). При переносе этой ветки нужно аккуратно разрешить конфликты.

## Порядок выкладки в production

1. **Бэкап** БД и **проверка восстановления** на отдельной копии.
2. На восстановленной копии: `prisma migrate deploy`, затем `MIGRATION_DATABASE_URL=<копия> node scripts/backfill-chat-threads.mjs` и `--check`. Замерить время и выборочно сверить пары.
3. Production: `prisma migrate deploy` (миграция короткая: DDL, истории по умолчанию, память одним оператором; `lock_timeout` 5 с, `statement_timeout` 300 с). `CHAT_THREADS_ENABLED` не задавать.
4. `MIGRATION_DATABASE_URL=<prod> npm run chat-threads:backfill` (пачками, можно запускать при работающем приложении).
5. Деплой кода с выключенным флагом. Смоук: старый чат открывается, сообщение отправляется, редактор памяти, перегенерация, `/chats`, гостевой чат и claim.
6. Повторно `chat-threads:backfill` (подбирает строки, записанные старым кодом во время выкладки), затем `chat-threads:backfill -- --check` → `ok: true`.
7. `CHAT_THREADS_ENABLED=1`, перезапуск. Смоук: список историй, новая история, переключение, переименование, архив, удаление тестовой истории, RU/EN, мобильная ширина, `threadHash` в новых `AiCostEvent`.

## Откат

- **Штатный:** `CHAT_THREADS_ENABLED=0` и перезапуск. Схему и данные не трогать. Пользователи видят по одной (последней) истории на персонажа; остальные истории сохраняются и вернутся при включении флага.
- **Возврат кода к версии до историй** (только при крайней необходимости, после бэкапа): `prisma/sql/chat-threads-rollback.sql`. Он восстанавливает уникальность `(userId, characterId)` и сохраняет все сообщения, но удаляет память и prompt state всех историй, кроме последней на пару. В сборке предыдущего кода папка этой миграции должна остаться (либо не выполнять `migrate deploy`).
