# Поиск причины зависания ответов DeepInfra

Добавлены наблюдения в обычные пользовательские и гостевые запросы, продолжение и перегенерацию. Инструмент сравнения запускает реальный транспорт и потребитель ответа с учётом затрат в памяти. Он не подключается к БД, не сохраняет сообщения и не списывает VC; DeepInfra может тарифицировать сами генерации.

## Диагностика обычного трафика

После выкладки кода ошибки `[ChatDiagnostics] attempt failed` автоматически содержат:

- `providerRequestId` из разрешённого заголовка DeepInfra, `providerResponseId` из SSE; их можно передать поддержке провайдера вместе с временем запроса.
- Настроенные `firstByteLimitMs`, `idleLimitMs`, `totalLimitMs` и фактические интервалы чтения `lastReadWaitMs`/`maxReadWaitMs`.
- Число порций тела `chunkCount`, размер/время последней порции и максимальную паузу между ними. Порция сетевого тела и SSE-кадр — разные вещи.
- Тип/кодировку ответа, HTTP-статус, нормализованный `retryAfterMs` (секунды или HTTP-дата). Произвольные заголовки и тело ошибки не сохраняются.
- Число активных запросов к провайдеру/модели в начале и в конце, включая служебные запросы (`intent`, `summary`, память, embeddings). Эти счётчики относятся к одному процессу, не ко всему аккаунту или кластеру. `processInstanceId` отделяет процессы и перезапуски.

Ошибки нестриминговых запросов пишутся как `service attempt failed` с `purpose`. Это позволяет отличить 429 анализа намерения/сводки от 429 генерации пользовательского ответа.

`consumer failed` уточняет локальную стадию: `read_upstream`, `parse_upstream`, `deliver_delta`, `validate_completion`. Для `TypeError` сохраняется разрешённый код причины (например, `UND_ERR_SOCKET`); произвольные сообщения исключений и стек не пишутся. Этот журнал включён и для гостей. Серверная обёртка вынесена из общего с браузером модуля.

Для временной трассировки успешных и неуспешных попыток включить на сервере:

```dotenv
CHAT_TRANSPORT_TRACE=1
```

В `[ChatTransport]` появятся `attempt started`, `headers received`, первые **20** `chunk received` и итоговый `attempt ended`. Итог учитывает все порции независимо от ограничения трассировки. `operationId`/`costEventId` связывают строки; несколько строк одной операции не являются отдельными сбоями. После сбора примеров установить `CHAT_TRANSPORT_TRACE=0`. Без переключателя подробная трассировка отключена, диагностика ошибок остаётся.

Пример чтения: `idleMs≈45000`, `lastReadWaitMs≈45000`, `hasText=true`, `hasDone=false` — очередное чтение ожидало данные до прерывания. При `consumer failed` на `deliver_delta` исследовать передачу ответа клиенту. При 429 смотреть `purpose`, ID провайдера, `retryAfterMs` и локальную конкурентность. Небольшое число локальных запросов не исключает нагрузку других процессов или перегрузку модели у провайдера.

## Сравнительный запуск

Если SSH/терминал контейнера недоступен, открыть `/admin/chat-diagnostics` на основном адресе сайта. Используется существующий `ADMIN_SECRET`, проверка Origin и запрет кэширования отчёта. Ключ вводится только в парольное поле и хранится в памяти страницы. GET лишь читает статус; POST после явного подтверждения оплаты резервирует один тест и запускает его через Next `after`, затем страница опрашивает результат. Доступны фиксированные Mistral Small 3.2 и Qwen 3 235B, искусственный диалог и один последовательный прогон direct/pipeline (до трёх обращений). Произвольные URL, сообщения и параметры не принимаются.

Учёт в памяти и сбор наблюдений привязаны к AsyncLocalStorage этого теста: соседние пользовательские запросы сохраняют обычный учёт. Переменные процесса и глобальный приёмник логов не меняются. Админский тест не создаёт строки AiCostEvent и не обращается к каталогу БД. Таймауты, повторы и обработчик ответа приложения используются настоящие. Отчёт содержит только числовые показатели и разрешённые диагностические признаки, ID и usage; тела/тексты исключены.

Один тест выполняется на процесс, после завершения действует пауза 60 секунд. Результат хранится 15 минут до следующего теста либо перезапуска. Это временная диагностика для постоянного Node-контейнера; при нескольких процессах лимит и результат относятся к конкретному процессу. Админская страница не проверяет полный пользовательский путь через БД, кошелёк, браузер и reverse proxy.

Сначала выполнить безопасный запуск без сети из корня репозитория:

```powershell
npm run diagnose:chat:stream
```

План показывает модель, размеры входа, ограничения и максимальное количество обращений. Реальные обращения включаются только явным `--live`. Ключ берётся из `DEEPINFRA_API_KEY`; `.env` автоматически не читается. Файл переменных можно явно указать через `--env-file`.

На **том же сервере/в том же контейнере**, где выполняется приложение, с установленными зависимостями репозитория:

```powershell
npm run diagnose:chat:stream -- --live --env-file .env --mode both --runs 1
```

Пример для Qwen:

```powershell
npm run diagnose:chat:stream -- --live --env-file .env --model Qwen/Qwen3-235B-A22B-Instruct-2507 --mode both --runs 1
```

Один запуск `both` делает один прямой запрос и до двух запросов обычного транспорта (существующий повтор до начала потока). Запросы идут последовательно. Верхний предел `--runs` — 3. Можно выбрать только `direct` или `pipeline`. Для сохранения вывода использовать игнорируемую Git папку `logs/`.

Оба пути отправляют одинаковые сообщения, модель и генерационные параметры приложения:

- `direct`: обычный `fetch` с общим SSE-парсером; без обёртки учёта, потребителя приложения, повторов и idle-таймера. Общий предел — 120 секунд, включая ожидание заголовков. Читает до EOF и требует корректного завершения протокола.
- `pipeline`: реальный `streamChatCompletion` и серверный `consumeOpenAIChatCompletion`, с обычными таймерами (заголовки 15 секунд, простой 20/45 секунд, попытка 120 секунд) и повторами. Учёт только в памяти.

Прямой вариант намеренно терпит паузы дольше обычных 15/20/45 секунд. Поэтому его успех при неудаче pipeline может указывать именно на политику таймаутов, а не на ошибку парсера. Это два независимых запроса к модели: один запуск не является доказательством причинной связи. Сценарий можно повторить с другой последовательностью, запуская отдельные режимы вручную.

По умолчанию используется синтетический русскоязычный диалог с контекстом. `--context-repeats 0..1000` меняет его длину. `--messages-file` принимает JSON-массив объектов `role`/`content` (не более 256 КБ, 200 сообщений); содержимое никогда не печатается. Переданный контекст отправляется DeepInfra, поэтому использовать его только в рамках разрешённого доступа к переписке. Хранить такие файлы в `logs/`, не в Git. Тексты запросов и ответов, cookies, ключи и тела ошибок не попадают в отчёт. В отчёте остаются технические ID, размеры и числовой usage, если он пришёл.

## Интерпретация результата

Если прямой запрос завершается, а pipeline нет, сопоставить время завершения direct с пределами приложения и стадией отказа pipeline. Если оба не завершаются, проверить соединение сервера и обратиться к DeepInfra с ID запросов. Повторить прямой вариант с другого компьютера, сохранив модель/контекст: устойчивое различие между компьютером и сервером указывает на путь соединения или окружение сервера; единичные результаты могут зависеть от загрузки провайдера.

Если оба завершаются, проблема не воспроизвелась. Нужны диагностические строки реального сбоя. Скрипт **не проходит через Next HTTP route, reverse proxy, браузер, БД и возврат VC**; для этих частей используются журналы обычного трафика, в том числе `consumer failed` и прежние стадии `save_reply`/`deliver_end`. Новый публичный диагностический API не создаётся.

Ответ 429 не доказывает превышение лимита именно этим процессом: DeepInfra также выдаёт 429 при высокой загрузке модели. Сведения провайдера: [streaming](https://docs.deepinfra.com/chat/streaming), [rate limits](https://docs.deepinfra.com/account/rate-limits).

## Проверки

`npm run verify:chat:transport` проверяет без внешней сети и БД идентичность запросов, позднее завершение direct против idle-таймаута pipeline, отсутствие повтора после частичного текста, нормализацию Retry-After, служебный 429, стадии ошибок доставки, предел трассировки и освобождение счётчиков. Прежние проверки протокола и Mistral остаются применимы. Реальные обращения к DeepInfra и выкладка требуют отдельного запуска; успешная искусственная проверка не устанавливает причину исторического сбоя.

В этой рабочей копии выполнены: новая проверка транспорта — 23 проверки, прежняя диагностика — 58, протокол потоков — 64, контролируемый Mistral — 101; TypeScript и ESLint изменённых файлов прошли. Production-сборка с синтетическими переменными прошла после разрешённого локального запуска вне файловой песочницы Windows (в песочнице Turbopack получил отказ доступа). Интеграционный `verify-cost-streams-runtime` не запустился: отсутствует отдельная установка embedded-postgres (`GUEST_TEST_RUNTIME`). Это ограничение тестового окружения; проверка БД/кошелька этим прогоном не подтверждена.

Первоначальная реализация проверена локально без живых API-запросов. По последующему запросу владельца релиз диагностики подготовлен поверх актуальной `main` (`d82233e`), с сохранением независимых историй чатов и без посторонних изменений редактора/промптов из основной рабочей копии. Для изолированной локальной проверки используются общие библиотеки и отдельный Prisma-клиент; временные настройки разрешения ссылок восстанавливаются перед коммитом и в деплой не включаются.

Первый диагностический релиз опубликован коммитом 3074499, включение CHAT_TRANSPORT_TRACE подтверждено оператором. Админский запуск добавлен отдельно для размещения без SSH. `npm run verify:chat:admin` проверяет авторизацию, Origin, запрет произвольных входов, резервирование задания, конкурентный обычный учёт, идентичность обращений, таймауты и приватность. Таймауты/повторы обычного приложения и правила оплаты не изменены; диагностика не добавляет миграций. Реальные результаты серверного сравнения оцениваются отдельно от искусственных проверок.
