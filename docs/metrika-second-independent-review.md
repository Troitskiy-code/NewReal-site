# Повторное независимое ревью Метрики

Дата: 1 октября 2026. Production, боевой счётчик, платежи, commit/push и ротация секретов не затрагивались. Код приложения не менялся.

Вердикт: основные сценарии предыдущих четырёх замечаний исправлены. Утверждение о полном закрытии P1 пока принимать нельзя: обнаружены два оставшихся P1 и два замечания P2.

## Что подтверждено

Новый независимый `docs/metrika-second-review-probe.cjs` исполняет настоящий runtime в отдельных VM-контекстах с текущими ключами storage и формой записей. API, Яндекс и storage подставные; время управляемое, heartbeat исполняется явно.

- Старый confirmed invoice 203 больше не перекрывает новый pending 204.
- Переключение A → B выбирает отдельный набор записей. Статический путь обработки pending теперь сбрасывает confirmed; unit-проверка этого пути прошла.
- Успешно завершённая VC-цель не повторяется при отказе записи ключа очереди в localStorage: одна отправка после двух poll.
- Две независимые вкладки: heartbeat продлевает lease; после 16 секунд вторая не начинает отправку, первая завершает callback. Это отдельная проверка времени, а не только конкуренции внутри исходного lease.
- Комментарий миграции исправлен: SQL до новой версии приложения.

Старый probe не годится для подтверждения этих исправлений: в нём остались прежний ключ без userId и VM без setInterval. Его раннее падение `0 !== 2` само по себе не доказывает исправление оставшихся сценариев. Новый probe учитывает текущие интерфейсы.

## P1: отказ localStorage отключает обработку покупки без Web Locks

Файл: `src/lib/purchaseGoalRuntime.ts:401`, `withInvoiceLock` начиная с 437, обработчик catch после releaseLock; capture в строках 339–340.

Тест Cursor бросает QuotaExceededError только при записи ключа очереди. Запись lock остаётся разрешённой. При настоящем отказе всех setItem в localStorage запись lease тоже не работает.

Независимое воспроизведение: navigator.locks отсутствует, localStorage.setItem бросает ошибку, sessionStorage полностью работает, счётчик готов. Capture успешно сохраняет invoice в sessionStorage и удаляет InvId из URL. Но pollAndDispatchInvoice возвращает null до вызова API: 0 запросов статуса, 0 целей. При повторных poll ситуация не меняется. Это потеря обработки даже в одной вкладке, а не только отсутствие гарантии exactly-once между вкладками.

Рекомендация: отделить возможность подтвердить invoice от возможности получить межвкладочную блокировку. Предусмотреть явно документированный режим деградации с рабочим sessionStorage/памятью и блокировкой в пределах вкладки либо иной доступный механизм. Не скрывать невозможность обработки за null; не удалять единственное восстановление URL, если выбранная стратегия не сможет обслужить сохранённую покупку. Добавить тест полного отказа localStorage при живом sessionStorage и без Web Locks.

## P1: ранжирование записей отменяет лимит повторных отправок

Файл: `src/lib/purchaseGoalRuntime.ts:170` — `goalRank` и `isFresherRecord`.

Ранг старого dispatched=4 всегда выше ранга нового timeout=3 независимо от updatedAt и attempts. Поэтому новая запись после timeout проигрывает старой записи, оставшейся в localStorage после отказа обновления очереди.

Независимое воспроизведение: localStorage содержит dispatched/attempts=1, более новый sessionStorage — timeout/attempts=2. Запись очереди в localStorage не работает, запись lock и sessionStorage работает. Пять следующих poll вызывают dispatchGoal пять раз. После каждого чтения снова выбирается attempts=1; sessionStorage сохраняет attempts=2. Политика maxDispatchAttempts=3 фактически не ограничивает отправку. При каждом настоящем timeout внешний сервис мог уже принять цель: риск дублей больше заявленного ограниченного retry.

Рекомендация: объединять состояние каждой цели отдельно, сохранять максимальное число попыток и терминальный callback_completed, а переход dispatched → timeout выбирать по версии/времени попытки. Не считать общий ранг записи хронологией. Добавить регрессии timeout/unknown при частичном сбое storage и проверить, что retry останавливается на лимите, включая reload.

## P2: старый async-ответ пишет запись в новый аккаунт

Файл: `src/lib/purchaseGoalRuntime.ts:553` и 557 — ветки после fetchStatus; upsert использует ключ текущего activeUserId.

Воспроизведение: A запускает poll invoice 303, затем logout → login B, после этого завершается fetch A. fetchStatus возвращает http=0 по generation, но poll всё равно делает upsertPendingPurchase старой записи A в scoped storage B. В B появляется запись userId=A, хотя новые обычные захваты URL правильно изолированы.

Чужая цель в этом тесте не отправлялась, а visibleToCurrentUser скрывает запись в баннере. Замечание относится к нарушению изоляции очереди и загрязнению состояния, а не к доказанной утечке серверного API или начислению.

Рекомендация: при смене generation прекращать обработку до любого persist/emit; зафиксировать владельца операции и проверять соответствие перед записью, включая http/catch ветки. Не записывать патч одного владельца под ключом другого.

## P2: старый баннер восстанавливается вне текущей сессии возврата

Файл: `src/lib/purchaseGoalRuntime.ts:313` — fallback по bannerSession; флаг записывается в durable purchase record при capture, строка 333.

Флаг bannerSession сохраняется в localStorage вместе с историей. Новая VM-вкладка с новым sessionStorage, без InvId и без локального bannerInvoiceId получает confirmed invoice 304 предыдущего посещения через resolveBannerRecord. Таким образом, понятие текущей сессии баннера по-прежнему живёт в durable storage до TTL. Logout сбрасывает bannerInvoiceId, но не сохранённый флаг.

Рекомендация: хранить активный баннер отдельно от долговременной дедупликации — например, в sessionStorage с явным завершением/сбросом. Сохранить нужное восстановление текущего возврата после reload, но не показывать старое подтверждение в новой сессии без текущей покупки. Проверить A → logout → A и новую вкладку без query.
