# Диагностика ошибок чата — 12 октября 2026

## Результат

В рабочей копии добавлено безопасное логирование ошибок генерации, обработки ответа и возврата VC. Оно поможет установить причину следующих сбоев DeepInfra, включая неполные SSE-потоки с HTTP 200. Причины исторических ошибок из приёмки автоматически не восстановлены; проблема стабильности не объявляется закрытой.

## Что записывается

- `[ChatDiagnostics] attempt failed`: провайдер, запрошенная модель, аудитория `user`/`guest`/`system`, этап сбоя, HTTP-статус, причина и безопасные поля исключения. При сетевом сбое сохраняется разрешённый код причины, например `ECONNRESET`.
- Таймауты различаются по существующим watchdog: `first_byte` (ожидание HTTP-заголовков), `idle` (пауза между чанками), `total` (общий предел). Прерывание и отмена потребителем выделены отдельно.
- Для начавшегося потока есть `headersMs`, `firstChunkMs`, `firstTextMs`, `durationMs`, `idleMs`, `bytesReceived`, `frameCount`, `hasDone`, `hasText`, `hasReasoning`, `finishReason`, `protocolReason`. Интервалы отсчитываются от начала обращения к провайдеру после локального учёта попытки. Отсутствующее первое событие — `null`.
- Протокольные причины: ошибка провайдера или SSE, некорректный JSON/тип данных, слишком большой кадр, неправильный порядок завершающих событий, фильтрация содержимого, неподдерживаемое завершение, отсутствие `[DONE]`/`finish_reason`, пустой видимый ответ. Текст рассуждений не сохраняется.
- `[ChatDiagnostics] response failed`: ошибки чтения/передачи потока, сохранения ответа, планирования памяти или отправки завершающего события в обычном чате, продолжении и перегенерации.
- `[ChatDiagnostics] retry scheduled`: запланированный существующим механизмом повтор до потока. `retryAttempt` — счётчик retry; `attempt` в записи провайдера — общий номер AI-вызова внутри операции, включая служебные запросы.
- `[ChatRefund] refund completed` / `refund failed`: фактический результат попытки возврата, сумма VC и локальный идентификатор транзакции. Успех пишется только после завершения транзакции БД.
- Ошибки записи `AiCostEvent` дополнены идентификаторами попытки и операции.

## Связь записей и безопасность

`operationId` связывает события одного запроса, `costEventId` соответствует `AiCostEvent.id`. При retry записи попыток разные, идентификатор операции общий. Возврат связывается через `operationId` и `transactionId`; для него контекст сохраняется при резервировании VC.

Новые диагностические записи не содержат промптов, переписки, ответов/ошибок провайдера, рассуждений, заголовков авторизации, ключей, email, стека или произвольного `Error.message`. Контекст ошибок проходит allowlist логгера, а исключения — `toSafeDiagnostic`. Console и диагностический sink получают одну безопасную строку. Ошибка sink не останавливает генерацию или учёт.

На одну неуспешную попытку провайдера пишется одна завершающая диагностическая запись. Ошибка обработчика и возврат — отдельные события той же операции: при подсчёте не следует складывать все строки как независимые сбои.

## Проверки

- `npm run verify:chat:diagnostics` — 58 проверок: реальные telemetry/logger с подставной БД и fetch, все три вида таймаута, отказ HTTP, пустой/оборванный поток, отмена, успешный и неуспешный возврат, отсутствие приватного содержимого в обоих каналах, отказ sink.
- `npm run verify:economy:streams` — 64 проверки; прежние правила принятия ответа сохранены, включая допустимый `finish_reason=length`.
- `node scripts/verify-cost-streams-runtime.mjs` — 66 проверок с реальными chat/regenerate handlers и одноразовым PostgreSQL: корреляция ошибок/возврата, неполный поток, ошибки сохранения ответа, продолжение/перегенерация, сохранность расходов и VC.
- `node scripts/verify-deepinfra.mjs` — 63 проверки с искусственным провайдером и изолированной БД, включая гостя, retry и таймаут после заголовков.
- `npm run verify:p0-security` — 113 проверок.
- TypeScript, ESLint изменённых файлов и `git diff --check` — exit 0. Синтетическая production-сборка — exit 0; это не проверка живого провайдера или production-БД.

## Границы изменения

Таймауты, повторные платные запросы, тарификация, цены моделей, правила сохранения/возврата VC и схема БД не изменялись. При отказе транзакции возврата появляется `refund failed`; автоматическое восстановление такого возврата этим изменением не добавлено.

Миграции, дополнительные переменные и cron для этой диагностики не нужны. Production, платные вызовы и настройки сервиса в этом задании не менялись. Коммит, push и деплой не выполнялись из этого чата. После выкладки диагностика доступна в обычных серверных логах Relaxdev и существующем sink.
