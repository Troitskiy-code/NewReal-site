# Память NewVerse: завершение первого этапа без миграции

Дата: 8 октября 2026. В плане памяти этот первый этап называется **этапом 0**. Статус: реализован в рабочей копии и прошёл локальные проверки. Production-приёмка и оценка ответов настоящей модели остаются отдельными действиями. Память v2 не реализовывалась.

Ревью 9 октября: дополнительно воспроизведена и исправлена гонка внутри SQL записи/отзыва embedding. Проверки расширены до 28 сценариев; разрешён выпуск кода первого этапа. Проверка production после выкладки остаётся отдельным действием.

Позднейшая приёмка 9 октября нашла пять дефектов на production. Исправления в рабочей копии: фильтр известных команд памяти, сохранение ручных core-фактов и условная транзакционная запись, актуальный ответ refresh после конфликта, сводка из проверенных исходных цитат, привязка расходов перегенерации/refresh. Локально: 36/36 сценариев и 67 проверок; восемь проверок прежних дефектов дают 0/8 на коммите `8503de8`. Подробности и ограничения: [отчёт исправлений](memory-production-review-fixes-2026-10-09.md). Выкладка и повторная живая приёмка этих исправлений остаются открытыми. Ниже сохранён исходный отчёт этапа 0.

## Что было проверено перед продолжением

Работа продолжена после исчерпания лимита Cursor. Сначала просмотрены статус Git, изменения относительно `2e09e7acbcb2e5da73297730c419fbe3950d104b`, исходные сценарии и промежуточные результаты Cursor. Существующие изменения SEC-04 и другие файлы рабочей копии сохранены.

Cursor уже изменил подготовку контекста в `chatHelpers.ts`, извлечение событий в `advancedMemory.ts`, сводки в `chatMemory.ts`, обработку core-памяти, semantic embeddings, RAG и обработчики обычного сообщения/перегенерации. Добавлены `memoryPromptFormat.ts`, `tokenCount.ts`, изолированный harness и сценарные проверки. В `package.json` появились команды памяти, а в devDependencies — `@electric-sql/pglite-pgvector` для тестов векторного SQL.

Среди оставшихся проблем обнаружены вытеснение необработанного хвоста заполненной памятью, перезапись ручной сводки фоновой задачей, устаревшие векторы изменённого сообщения и порядок эпизодов по завершению фоновой обработки. Эти случаи исправлены и включены в регрессионные проверки.

## Итоговые изменения

### 1. Отбор событий после определения намерения

`src/lib/advancedMemory.ts` загружает до десяти кандидатов независимо от intent, с ограничением важности по доступному контексту. `src/lib/chatHelpers.ts` выбирает окончательный набор после определения intent: сюжет/действие — до десяти событий, general — до трёх, fact/question — до двух. Это верхние границы: токеновый бюджет может сократить набор.

Сначала события выбираются по важности и актуальности, затем выбранные события подаются в хронологии. Новые эпизоды сохраняют время исходного хода пользователя, а не момент завершения фоновой AI-обработки. Параллельные задачи не переставляют последовательность «нашли ключ → потеряли ключ». Исторические timestamps автоматически не переписываются.

### 2. Поиск по репликам пользователя и персонажа

`src/lib/messageEmbeddings.ts` ищет среди обеих ролей с фильтрацией по пользователю и персонажу. В контексте цитата содержит автора. Цитаты, уже присутствующие в выбранном окне истории, повторно не добавляются.

RAG разрешён только подходящим планам. Кроме fact/question, он включается для истории длиннее 3000 токенов. Загруженное окно считается точно; для более старых сообщений используется оценка по их числу и среднему размеру сообщений в окне. Это оценка полного объёма, а не полный подсчёт каждого исторического сообщения.

HTTP-запрос embedding для поиска имеет timeout 3 секунды. Ошибка embeddings даёт пустой результат поиска и позволяет чату продолжить работу. Этот timeout не является общей гарантией времени ответа сайта или времени SQL-запроса.

Для continue/regenerate устаревший embedding отзывается даже при смене плана, запрещающей новые embeddings. Новая запись вектора атомарно проверяет, что исходный текст всё ещё совпадает с текущим сообщением. Запоздалый ответ провайдера для старого текста не сохраняется; запоздалое обновление старой версии не удаляет вектор новой версии. Перегенерируемая реплика исключается из поиска для нового ответа.

Ревью 09.10 обнаружило, что одной проверки текста в SQL snapshot недостаточно: UPDATE мог завершиться между чтением текста и фиксацией INSERT. Native PostgreSQL probe воспроизвёл один оставшийся старый вектор. Теперь INSERT и DELETE удерживают `FOR SHARE` на исходном сообщении до завершения своего короткого SQL-запроса. Provider-вызов выполняется до этого запроса и не удерживает блокировку. Сценарии S13d/S13e проверяют конкуренцию записи и отзыва с UPDATE на настоящем PostgreSQL; [воспроизведение до исправления](memory-stage-0-review-race-before.json).

### 3. Необработанный хвост и подтверждённое покрытие сводки

Покрытие истории определяется только `lastSummarizedAt`. Дата создания строки сводки и наличие произвольного текста не доказывают, что сообщения обработаны.

В пределах загруженного окна приоритет получает непрерывный хвост последних необработанных сообщений. При нехватке контекста сначала убираются старые цитаты, сводка, события и core. Подготовка фиксирует число отброшенных необработанных сообщений и блоков памяти. Последняя реплика сохраняется.

Хвост ограничен окном истории плана и бюджетом контекста модели. Если системный промпт вместе с последней репликой сам превышает бюджет, сборщик отмечает превышение; в этой ситуации он не гарантирует допустимый размер запроса. Изменение не означает безлимитную историю или сохранение всех сообщений в каждом запросе.

Сводка обрабатывает старейшую ещё не покрытую часть истории порциями до 120 сообщений, оставляя последние 25 вне новой главы. Группа сообщений с одинаковым timestamp не разделяется границей покрытия. Успешная запись сравнивает прежние timestamp и текст сводки; проигравшая параллельная задача пропускает запись. При ошибке сводки покрытие не продвигается.

Ручная замена сводки очищает подтверждённое покрытие и счётчик обработанных сообщений. Фоновая задача, читавшая старую сводку, не может затереть эту правку, даже если timestamp отдельно остался прежним.

### 4. Полный ход диалога и граница данных

Обычный завершённый ход передаёт классификатору сообщение пользователя и ответ персонажа: ответ может содержать обещание или событие мира. Указание источника сохраняет отличие от фактов самого пользователя. В обновление Core передаётся только текст пользователя. При неудачной генерации возможна обработка пользовательской части; continue/retry не запускают повторное извлечение памяти для того же пользовательского хода.

Ручная core-память при записи и чтении проходит согласованную структурную нормализацию и ограничение размера. `memoryPromptFormat.ts` оформляет память как данные в отдельных блоках, нейтрализует управляющие символы и попытки закрыть/открыть маркеры блоков. Доверенный текст промпта указывает не исполнять инструкции внутри памяти и предпочитать последние сообщения при противоречии.

Это структурная мера снижения риска. Изолированный тест проверяет оформление промпта, но не доказывает, что настоящая модель никогда не последует вредоносной инструкции.

### 5. Консервативное удаление дублей и учёт

`memoryEmbeddings.ts` учитывает имена в начале предложения, сохраняет различие длинных имён с одинаковыми первыми буквами и различает утверждение/отрицание. Различие имён, чисел или отрицания препятствует автоматическому semantic merge. При отказе embeddings fallback ограничивается существующими пределами сводки и числа событий.

Это предотвращает часть ложных слияний. Старое имя не превращается автоматически в факт со статусом superseded: модель активных фактов относится к v2. Консервативный алгоритм может сохранять лишние перефразировки.

Токенизатор переиспользуется внутри процесса. Embeddings, intent, классификатор, core и сводки проходят существующий учёт `AiCostEvent`. Дополнительные поиски по длинной истории могут повысить число вызовов и расход; экономия или ускорение на production этим изменением не заявляются. Цены, правила списания VC и квоты подписок не менялись. Сырые ошибки памяти передаются через безопасную диагностику; фрагмент продолжения диалога удалён из console-лога.

Native race-сценарии исполняют SQL записи/отзыва на PostgreSQL 18 с текстовым domain вместо vector: они проверяют реальную конкуренцию строк, а не расстояния векторов. AI-ответы и embeddings подставные. `.env` и production-БД не используются, реальные платные вызовы не выполнялись. PGlite не заменяет проверку расширения pgvector на целевом PostgreSQL.

## Что остаётся за пределами первого этапа

- Память по-прежнему привязана к пользователю и персонажу. Независимых историй с одним персонажем и `ChatThread` пока нет.
- Core остаётся текстовым блоком; нет структурированных active/superseded/retracted фактов, версий сводок и точного отката событий/Core при перегенерации.
- Извлечение события ограничено одним значимым событием на ход и усечённым входом классификатора. Это не полная модель мира, знаний NPC и лора.
- Фоновые вызовы остаются best effort: нет durable `MemoryJob`, очереди и гарантированного retry после рестарта. Обновления Core не получают версионирование фактов из v2.
- Старые сводки и события не очищаются автоматически от прежних ошибок; исторические embeddings не достраиваются массово.
- Нужны живая оценка ответа, TTFT/latency и сверенная себестоимость на сопоставимых сценариях. Успешные заглушки не закрывают весь RET-01.

Подготовлены `scripts/memory-live-eval.mjs` и [контрольные сценарии](memory-live-scenarios-2026-10-08.json). Runner требует явное подтверждение платного запуска и переданный API key, не читает `.env`. **Не запускался.** Часть оценок требует ручного чтения ответа; проверка по ключевым словам также не является окончательной оценкой качества.

## Выпуск и ручная приёмка

Новая миграция, cron или переменные окружения для этого этапа не требуются. Используется существующая схема памяти и embeddings. На завершение реализации 08.10 коммит/push не выполнялись; 09.10 владелец разрешил их после ревью. Production-приёмка по-прежнему не выполнена. Откат — возврат предыдущей версии приложения; изменения схемы БД отсутствуют.

После выкладки проверить на длинном диалоге своего аккаунта:

1. Обычный ответ, продолжение и перегенерация завершаются; нет двойного списания за один запрос.
2. Персонаж помнит названное имя, собственное обещание и порядок двух событий. Контрольный вопрос не должен подсказывать правильный ответ.
3. Ручная правка сводки сохраняется после фонового обновления; перегенерация не извлекает старый текст из embedding.
4. В `AiCostEvent` записываются новые chat/memory/embedding попытки, нет новых ошибок отсутствующих таблиц/колонок. Сопоставить расходы и время ответа до/после на близкой длине диалога.

Эти действия также перечислены владельцу в чате. Память v2 остаётся следующим проектом; она не включается этим выпуском.
