# Повторное независимое ревью P0/P1 — 1 октября 2026

**Вердикт:** ответ Cursor точнее предыдущего, но «код по замечаниям ревью исправлен» — слишком сильное утверждение. Помимо названных им операционных шагов остались воспроизводимые ошибки кода. P0/P1 не готовы к приёмке.

- `npm run verify:p0-p1:repro`: passed. Важно: теперь скрипт проверяет чистую policy-функцию, а не прежний реальный API handler со stub-БД.
- `npm run verify:p0-p1:int`: passed 37 checks на **новом временном локальном PostgreSQL 18.4**, запущенном независимым wrapper на свободном порту. Исходный автоматический запуск БД не использовался. Повторён и тест upgrade, но он имеет ограничения ниже.
- `npx tsc --noEmit`: passed.
- `npm run build`: passed с предупреждением Turbopack о трассировке проекта. Запуск использовал синтетические DATABASE_URL/NEXTAUTH_SECRET; недоступная локальная БД вызвала диагностические ошибки sitemap/runtime DDL, но сборка завершилась. Это проверка сборки, не работоспособности с настоящей схемой.
- `npm run lint`: 27 errors / 25 warnings. Сравнение проблемных файлов с HEAD: 25 errors уже есть в базовых версиях этих файлов, **две относятся к изменениям P0/P1** — SupportPage и новый PurchaseStatusBanner. Следовательно, все 27 нельзя называть прежними.
- В verify-скрипте прежние литералы удалены; из тарифов удалены обещания очереди, суммы цен и пакетов VC сохранены. Появились уникальный PaymentEvent, долговечное состояние доставки тикета, payload binding и серверный revoke; оценка тарифов действительно читает каталог.

Продакшен, реальные списания, внешние платёжные/почтовые сервисы и браузерный пользовательский сценарий не использовались. Приложение не исправлялось. Проверочные документы и независимые harness добавлены в docs.

## 1. P0 — логирование всё ещё раскрывает секреты

`src/lib/redactSensitive.ts:4–5,23–27,63`:

- `Authorization: Bearer SYNTHETIC_AUTH_VALUE`: маскируется слово Bearer, значение токена остаётся.
- `password="SYNTHETIC_PASSWORD_VALUE"`: значение в кавычках не маскируется.
- DSN и `token=SYNTHETIC_TOKEN_VALUE` в одной строке: ветка DSN делает ранний return, обработка token не выполняется.

Все три случая воспроизведены с синтетическими значениями. Циклический массив также вызывает RangeError: Array обрабатывается раньше регистрации в WeakSet (`redactSensitive.ts:82`). Тест «handles cycles» проверяет только plain object.

`src/lib/auth.ts:158` по-прежнему выводит сырой error от Adapter.linkAccount через console.error, обходя logger; такая ошибка может включать параметры записи OAuth. Остальные прямые auth/Prisma error-логи также не сводятся исключительно к безопасным id/provider, как можно понять из отчёта Cursor.

**Исправление:** на чувствительных путях разрешённые поля ошибок без сырых message/args/config; все прямые auth/OAuth-логи провести через безопасный путь. Если текстовый scrub сохраняется, обработать Bearer, кавычки и несколько секретов независимо от DSN. Добавить тесты перехваченного вывода и циклического массива. Ротация production остаётся отдельным незакрытым пунктом.

## 2. P1 — проигравший конкурентный retry расходует ещё одну quota

`src/lib/guestRequestStore.ts:124–139,166–188`: обе транзакции читают failed с refundedAt, затем обе резервируют quota. Одна выигрывает update с fencing; вторая получает count=0 и возвращает in_progress, **но её резервирование коммитится**.

Детерминированное воспроизведение на PostgreSQL с барьером между чтением failed и резервированием:

`before=0, after=2, kinds=[run,in_progress], expectedQuota=1`.

37 tests замечают одного runner, но не проверяют счётчик после конкурентного retry. Исходный недетерминированный запуск мог пройти без нужного interleaving.

**Исправление:** владение попыткой и quota должны фиксироваться вместе. Проигрыш fencing должен отменять reservation, а не завершать транзакцию нормальным return. Добавить проверку счётчика и вынужденной конкуренции.

## 3. P1 — старый failure handler возвращает quota новой попытки

`guestRequestStore.ts:55–69,207–222`: обработчик читает pending attempt=1; другая транзакция успевает получить attempt=2. UPDATE по attempt=1 меняет 0 строк, но результат не проверяется. Затем refund выполняется по sessionId/requestId без attempt и помечает **новую** попытку refunded.

Воспроизведение:

`newKind=run, attempt=2, status=pending, quota=0, refunded=true`, хотя для новой активной попытки quota должна быть 1.

Это нарушает fencing и допускает генерацию без занятого места лимита.

**Исправление:** возврат привязать к конкретной попытке/reservation; выполнять его только после успешного атомарного изменения состояния именно этой попытки. Отдельно проверить old fail vs new retry, old fail vs finalize и два одновременных fail.

## 4. P1 — userRow и указатель запроса по-прежнему записываются раздельно

`src/lib/anonymousChat.ts:302–317`: create AnonymousMessage коммитится до update AnonymousChatRequest.userMessageId. Если update падает, запрос помечается failed и quota возвращается, но userRow остаётся без ссылки. Retry с userMessageId=null создаст ещё один userRow. При переносе оба будут выбраны по requestId завершённого запроса.

`anonymousChat.ts:325–347`: чтение userRow, модели и истории после claim остаётся вне общего catch. Ошибка БД оставляет pending и reservation до дальнейшего retry/transfer; отдельного фонового восстановления lease для гостевых запросов нет. Вывод по коду; сбои этих конкретных API-операций интеграционный тест не внедряет.

**Исправление:** userRow и привязку к попытке записывать одной короткой транзакцией с fencing; общий безопасный обработчик исключений после claim и определённый recovery. Проверять handler целиком с отказом каждого этапа, а не только store-функции.

## 5. P1 — перенос на клиенте прекращается раньше завершения генерации

`src/app/chat/[id]/ChatPageClient.tsx:929–938`: после in_progress клиент ждёт 1,5 секунды и повторяет POST один раз. Если генерация длится дольше, вторая ошибка проглатывается; далее загружается пользовательский чат без перенесённой истории. Новый перенос ожидается только после следующей загрузки страницы.

Серверный in_progress — полезная защита от неполного копирования, но без рабочего ожидания/повтора клиентская проблема не закрыта.

**Исправление:** ограниченное ожидание с retry/backoff, видимым статусом и явным дальнейшим действием; успешный перенос должен обновить историю без ручного reload. Проверить вход одновременно с генерацией на настоящем браузере.

## 6. P1 — миграция и её тест не доказывают сохранение поведения старых данных

`prisma/migrations/20261001180000_p0_p1_rework/migration.sql:4–7`: для существующих запросов payloadHash становится пустой строкой, reservedQuota=false, leaseUntil=null. Нет backfill hash из characterId/userContent. Обычный повтор старого completed получает REQUEST_CONFLICT. Старый pending требует отдельной политики восстановления quota. Это проблема upgrade с данными первой реализации; наличие таких таблиц в текущем production не проверялось.

Upgrade-тест проверяет **наличие колонки и таблицы**, а не корректность этих состояний. Его исторический Transaction fixture использует `LIMIT 0` (`scripts/integration-p0-p1.ts:229`) и не создаёт платёж; значит SQL-backfill исторического платежа в этом upgrade-тесте не проверен. Отдельный тест backfillPaymentEventsFromTransactions проверяет другую реализацию на другой БД.

Полный migrate deploy чистой БД отсутствует из-за baseline; это Cursor честно указал. Runtime-роль тестируется прямым pg SELECT/CREATE, а не полным приложением. Prisma extension по-прежнему запускает DDL на операциях Character/Notification/EmailVerificationToken.

**Исправление:** backfill/явная политика для старых request states, настоящие исторические fixtures и проверки поведения после upgrade, поддерживаемый baseline/порядок миграций. Проверить приложение с ролью без DDL, включая auth, персонажей и уведомления.

## 7. Проверочные скрипты имеют ограничения и опасный default

- `scripts/browser-p0-p1.ts` использует только fetch. Нет браузера, ввода в формы, credentials login, register, transfer, logout или webhook→confirmed. Установка TEST_BASE_URL не добавит эти сценарии. Не задать URL — корректно для защиты production, но сам подготовленный скрипт не выполняет обещанную цепочку.
- Проверка первого гостевого ответа не проверяет end/сохранённый текст; отсутствие spoofed в ответе не доказывает, что upstream не получил подставленную историю. Anonymous payment-status допускает 200 и не проверяет содержимое ответа.
- В интеграционном payment test функция grant написана прямо внутри теста; фактический webhook, обработка подписи, commitPaymentGrant и ветки подписок не вызываются. Это доказывает уникальный ключ БД, но не весь платёжный путь.
- Outbox-проверка сначала захватывает тикет одним worker, затем запускает два worker на уже недоступном sending. Это не проверяет двух конкурирующих worker на одном due-тикете.
- Автоматический embedded-start (`integration-p0-p1.ts:86–88`) **останавливает любой процесс на порту 55432**. Так можно остановить чужую БД/сервис. Также удаляется фиксированный temp dataDir; при произвольном имени TEST_DATABASE_URL замена upgradeUrl может оставить тот же адрес для destructive upgrade. Поэтому повторять default-скрипт как безопасный универсальный запуск нельзя. Независимый wrapper выбрал свободный порт и новый каталог, указав ожидаемое отдельное имя БД.

**Исправление:** реальный Playwright-сценарий на отдельном сервере с тестовой БД/stub-провайдерами; HTTP-тесты настоящего webhook; детерминированные concurrent tests. Тестовый PostgreSQL должен принадлежать текущему запуску, с отдельным каталогом/портом и finally-stop; не завершать посторонние процессы и не применять destructive upgrade к тому же адресу.

## 8. P1 — идемпотентность поддержки не переживает reload клиента

`src/app/support/page.js:26–40,59`: в sessionStorage сохраняются topic/email/message, но не clientKey. После принятия тикета и потери ответа пользователь обновляет страницу; черновик восстанавливается, ключ создаётся новый и повтор создаёт второй тикет. Серверная идемпотентность работает, пока клиент сохраняет прежний ключ.

Outbox долговечный, cron присутствует — это подтверждённое улучшение. Но нет предела попыток/терминального статуса и рабочего интерфейса или alert для окончательно недоставляемых заявок; `lastError=delivery_failed` недостаточно для гарантии наблюдаемости оператором. Resend idempotency key не используется. Эти ограничения не покрыты тестом fail→retry→sent.

**Исправление:** сохранять ключ вместе с черновиком и исходным payload до подтверждения, затем менять для нового обращения; определить retry/dead-letter и видимость ошибок доставки. Общий rate limit остаётся незавершённым, как Cursor и сообщил.

## 9. Экономика — воспроизводима, но модель пока не обосновывает рекомендацию

Допущения честно помечены, RAG OR-флаг исправлен, текущие цены не изменены. Однако:

1. `scripts/economy-acquisition.ts:247` считает число платных запросов по 5 VC при доле дорогой модели <=30% и по 50 VC при >30%. Стоимость запроса при этом смешанная. Переход от 30% к 31% снижает число запросов в десять раз; это не согласованная модель расходования общего VC. Нужна стоимость и VC по каждой модели либо обоснованный взвешенный расход.
2. `firstPackVcFor:200–204` считает cost, но использует его только для проверки >0. Пакет получает 60/90/120/150 VC по выбранному сценарию, а не по бюджету себестоимости. Утверждение «VC из COGS» неверно. Сравнение сценариев одного пакета должно сохранять один и тот же продаваемый объём, меняя потребление/затраты; оптимизацию объёма следует рассчитывать отдельно.
3. `promoAi:249,270` вычисляется и затем полностью отменяется как `+promoAi-promoAi`; без включения промопотребления в другой показатель это исключает расходы промобонусов, а не предотвращает двойной счёт.
4. 25%-перенос начисляет liability каждому варианту, включая control без переноса, без моделирования eligibility/расхода/срока. Реферальная программа и отдельные картинки представлены описаниями, а не рассчитанными вариантами.
5. Выбор первого эксперимента 129 ₽ не выведен из результатов, минимальная выборка 400 оплат не обоснована ожидаемым эффектом. Stop condition не ограничивает накопленный расход бюджетом 40 000 ₽. Этот расчёт можно использовать как черновик, но не как основание запуска.

**Исправление:** согласовать VC и AI-cost по моделям; выбрать фиксированный пакет из допустимого COGS; учитывать проморасходы, перенос/рефералов; sensitivity при сопоставимом трафике и фиксированных условиях; бюджетный stop-loss, критерии успеха и выборка. Новые публичные условия по-прежнему не применять автоматически.

## Что передать Cursor

Начать с пунктов 1–3: убрать утечки и исправить обе воспроизведённые гонки. Затем выполнить пункты 4–8 и исправить математические ошибки §9. Переименовать статусы «исправлено и проверено», которые подтверждаются только policy/helper или структурой схемы. Две lint-регрессии исправить; прежний lint-долг обозначить отдельно. Не выполнять production-ротацию/миграции/платежи/релиз в рамках доработок. После исправлений повторить проверки с принудительными interleaving и пройти настоящую браузерную цепочку на тестовом окружении.

Доказательства: `docs/p0-p1-second-review-repro.mjs`, его `.log`, `docs/p0-p1-second-review-lint-summary.json`. В wrapper барьеры меняют только расписание обращений к настоящим транзакциям; решения, updateMany и refund выполняются исходным кодом проекта.
