# Задание Cursor: закрыть P0 по секретам и логированию

Работай в текущем репозитории. Выполни только исправления P0: исключи секреты из кода и диагностического вывода, добавь доказательные проверки и подготовь точный порядок production-ротации. Это задание ограничивает область работ из предыдущего большого задания P0/P1.

## 1. Границы работы

- Не изменяй Яндекс Метрику, цели покупки, цены, VC, экономику, платёжную логику, гостевые лимиты/перенос, поддержку или UX. Не исправляй остальные замечания P1 и общий долг lint.
- В auth, cron, почтовых и платёжных обработчиках разрешены изменения безопасного логирования; бизнес-поведение сохраняй.
- Не выполняй production-ротацию, миграции, релиз, списания, отправку писем, реальный OAuth и изменения Git history. Не коммить и не пушь автоматически.
- Не выводи секреты, их части или действующие connection strings в терминал, отчёт, тестовые fixtures, diff-примеры и сообщения коммита. `.env` не копируй и не добавляй в Git.
- Перед изменениями прочитай применимые AGENTS.md. Перед изменением Next.js-кода прочитай соответствующую документацию установленной версии в `node_modules/next/dist/docs/`.
- Сначала проверь актуальное состояние файлов: номера строк и старые отчёты могут отставать от текущего кода. Сохрани чужие изменения.

Основание: раздел 1 `docs/p0-p1-second-independent-review.md`. Остальные разделы этого ревью в данное задание не входят.

## 2. Исправить безопасную обработку ошибок и строк

Искать в `src/lib/redactSensitive.ts` и `src/lib/logger.ts`.

Подтверждённые случаи, которые должны стать безопасными:

```text
Authorization: Bearer SYNTHETIC_AUTH_VALUE
password="SYNTHETIC_PASSWORD_VALUE"
postgresql://synthetic:synthetic@localhost/test token=SYNTHETIC_TOKEN_VALUE
```

Сейчас обработка Bearer может скрыть слово `Bearer`, сохранив токен; кавычки обходят маскирование; ранний return после DSN оставляет другой секрет в той же строке. Циклический массив вызывает RangeError, поскольку массив обрабатывается до регистрации в WeakSet.

Рекомендации:

1. На чувствительных путях используй фиксированное сообщение и разрешённые диагностические поля: категория ошибки, проверенный код, числовой HTTP status, внутренний correlation ID. Не передавай сырой Error и его `message`, `stack`, `cause`, `meta`, query args, headers, request/response/config/body. Prisma/Axios и ошибки OAuth должны иметь отдельные безопасные представления. Произвольные `name`/`code` тоже могут содержать данные: валидируй допустимый формат и длину либо заменяй фиксированной категорией.
2. Если текстовая очистка сохраняется для остальных логов, обработай Bearer, значения в одинарных/двойных кавычках и без кавычек, несколько DSN и несколько секретов в одной строке. Обрабатывай все правила без раннего возврата после DSN. Не считай регулярные выражения гарантией безопасности произвольной внешней ошибки.
3. Учитывай регистр ключей и вложенные объекты, массивы, Map; регистрируй массивы в обходе циклов. Ограничь глубину/объём диагностического представления. Ошибка сериализации должна давать безопасную фиксированную заглушку, без fallback к исходному объекту или `String(rawError)`.
4. И console, и Logtail должны получать одно безопасное представление. Не оставляй обход очистки через форматирование, prefix или fallback. Prefix делай постоянным для каждого места вызова. Ошибка логгера не должна раскрывать исходные данные или ломать обработку запроса.

## 3. Убрать обходы безопасного логгера

Проверь как минимум следующие файлы и связанные обработчики:

- `src/lib/auth.ts`: `Adapter.linkAccount` (в предыдущем ревью около строки 158), `Adapter.createUser`, `signIn`, обновление emailVerified, обработчики Google и активации подписки. Везде замени сырой вывод ошибок на безопасные события. Проверь также logger/debug конфигурацию NextAuth: библиотечные ошибки не должны обходить защиту. Не меняй callbacks, права доступа и семантику авторизации.
- `src/lib/prisma.js`: прямые `console.error(..., error)` в обработчиках инициализации/DDL и расширениях. Отдельно проверь настройку PrismaClient `log`: встроенный вывод `error`/`warn` в stdout обходит приложение и может печатать аргументы запросов. Отключи такой вывод либо используй безопасный обработчик событий. Не создавай циклический импорт logger ↔ prisma; сохрани singleton, транзакции и расширения. Перенос runtime DDL в миграции — отдельная задача, здесь его не рефактори.
- `src/lib/email.ts`: в логах допустим домен, но не полный адрес, тело письма, ссылка сброса/подтверждения, код или ключ Resend.
- `src/app/api/cron/cleanup-anonymous/route.ts`: не логируй `CRON_SECRET`, переданное значение, начало/конец секрета или другую маску с фрагментами. Достаточны имя проверки и факт наличия/несовпадения. Не меняй контракт cron в рамках этой задачи.
- Остальные `src`-обработчики с console/logger: исключи сырые OAuth/provider/Prisma/Axios ошибки, Authorization, cookie, платёжные секреты и URL с credential-параметрами. Меняй только диагностику, без изменения обработки платежей и других P1-сценариев.

Для первичного поиска используй `rg -l` по именам файлов, чтобы не печатать потенциально чувствительное содержимое. Проверь `console.*`, вызовы logger, `log:` у Prisma, `error.message`, `error.stack`, `JSON.stringify(error)` и библиотечные debug-настройки. Ограничь поиск нужными исходниками; `.env` и старые секреты из Git history не выводи.

## 4. Проверить конфигурацию и кандидат коммита

Файлы: `src/lib/requireEnv.ts`, `src/lib/auth.ts`, `src/lib/prisma.js`, `.gitignore`, примеры env, скрипты проверки и документация.

- Сохрани обязательные `NEXTAUTH_SECRET` и `DATABASE_URL`, отсутствие литералов/fallback и ошибку отсутствующего env только с именем переменной.
- Проверь все файлы предполагаемого коммита, включая новые docs и scripts. Не ограничивай проверку двумя исходными файлами или regex на длинный hex.
- Проверяй реальные утечки без включения старых значений в тесты и отчёт. Вывод сканера: путь, строка, правило, статус; без значения совпадения. Примеры env содержат только очевидные placeholders.
- Подтверди, что реальные env-файлы и логи с секретами игнорируются и не отслеживаются. `.env.example` с placeholders может отслеживаться.
- Удаление литералов из текущего дерева не удаляет их из истории и не заменяет ротацию. Перезапись истории не выполняй; при необходимости опиши её отдельно как решение владельца.

## 5. Добавить самостоятельные проверки P0

Добавь `scripts/verify-p0-security.ts` и `npm run verify:p0-security` либо равноценный отдельный набор тестов. Существующие команды P0/P1 сохрани. Все значения в новых тестах — синтетические, внешние сервисы — mock.

Обязательные регрессии:

- Bearer; password/token в одинарных и двойных кавычках и без них; DSN + token в обоих порядках; несколько DSN/секретов; ключи Authorization/cookie/password/token разного регистра и вложенности.
- Циклические объект и массив, смешанный цикл, вложенные массивы/Map; сбой сериализации без утечки и падения запроса.
- Generic Error, Prisma/Axios-подобные ошибки, `cause`, config, headers, query args и вложенные OAuth-данные. Проверяй отсутствие каждого синтетического секрета в окончательном выводе, а не только наличие `[REDACTED]`.
- Перехват фактического `console` и mock Logtail через настоящий logger. Ветка ошибки `Adapter.linkAccount`/`createUser` и путь диагностики Prisma должны быть проверены через используемый код, а не копию функции в тесте. Если для тестирования нужен небольшой внутренний helper, он должен использоваться и в рабочем пути.
- Отдельные проверки обязательных env: отсутствие каждой переменной даёт безопасную ошибку без других значений конфигурации. Не запускай эти проверки с production env.

Выполни новый набор P0, `npm run verify:p0-p1`, `npx tsc --noEmit`, lint изменённых файлов и `npm run build`. Общий lint можно зафиксировать как существующий долг; не добавляй ошибок в изменённых файлах.

Запускай проверки в изолированной конфигурации с синтетическими секретами, локальной тестовой БД или mock, исключив автоматическую загрузку production URL из `.env`. Для сборки явно подставь безопасные локальные DATABASE_URL/DIRECT_URL и необходимые env. Недоступная БД и успешная сборка не доказывают работоспособность приложения. Не запускай прежний интеграционный скрипт с остановкой чужого процесса на фиксированном порту; для этой задачи он не требуется.

## 6. Подготовить production-ротацию, но не выполнять её

Подготовь отдельный runbook для владельца/оператора в `docs/p0-security-rotation-runbook.md`, адаптированный к реально используемой конфигурации проекта. Не вставляй реальные секреты или команды с их значениями.

Нужно описать:

1. Какие приложения, инстансы, workers и служебные команды используют NEXTAUTH_SECRET, DATABASE_URL и, если применяется, DIRECT_URL. Где оператор должен обновить конфигурацию.
2. Получение нового криптографически стойкого auth-секрета и пароля БД, хранение через секреты платформы. Ожидаемый выход пользователей из старых сессий при смене NEXTAUTH_SECRET.
3. Согласованный порядок изменения пароля БД, env и перезапуска всех потребителей. Учти окно, когда старые соединения ещё работают, а новые со старым паролем уже не подключаются; не обещай бесшовную ротацию без поддержки платформы. Не меняй данные, схему и права БД ради ротации.
4. Проверки после смены: новый вход и сессия работают, старая сессия не принимается, новое подключение со старым паролем БД отвергается, приложение подключается с новым, в новых логах нет credentials. Проверки выполняет оператор; вывод содержит только статус, без значений.
5. Действия при сбое и восстановление работоспособности с безопасными новыми credentials. Не предлагай возвращать раскрытые секреты или постоянно принимать старый auth-секрет.
6. Форму подтверждения: среда, время, ответственный, перечень обновлённых потребителей и результаты проверок. Работа с ранее опубликованными логами/историей — отдельный план, без автоматического удаления.
