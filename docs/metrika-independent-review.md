# Независимое ревью ответа Cursor: Метрика и циклический логгер

Дата: 1 октября 2026. Проверена текущая рабочая копия, без commit/push, production-миграций, реальных платежей и отправки целей в боевой счётчик.

Вердикт: исправление логгера подтверждено. Основные сценарии Метрики работают, но задачу нельзя закрывать до исправления четырёх воспроизведённых дефектов ниже.

## 1. P1: баннер игнорирует новую покупку

Файл: `src/components/PurchaseStatusBanner.tsx`, строки 20–29.

Хук выбирает последнюю сохранённую покупку и затем принимает обновления только с тем же invoiceId. Если в состоянии уже находится подтверждённый invoice 203, событие новой, ещё pending покупки 204 игнорируется: хук продолжает возвращать `{status:"confirmed", invId:"203"}`.

Это может показывать пользователю успех предыдущей покупки, пока новая ещё не подтверждена. Сохранённые подтверждения живут семь дней; выбор последнего элемента не устанавливает связь с текущим возвратом из оплаты.

Рекомендация: отдельно определять текущий invoice и владельца баннера; переключать его при новом возврате/событии покупки, очищать при logout и смене пользователя. Завершённые записи для дедупликации не должны автоматически становиться активным баннером. Проверить обновление состояния React без повторного использования изменяемого объекта.

## 2. P1: сохранённое подтверждение переносится между аккаунтами

Файл: `src/lib/purchaseGoalRuntime.ts`, строки 178–197; ветка pending в `pollAndDispatchInvoice`; `confirmationStatusOf`.

Воспроизведение: пользователь A подтвердил invoice 202; пользователь B открывает URL с тем же invoice. `captureInvoiceFromUrl` заменяет userId на B, сохраняя confirmed=true, kind и сумму. API текущего пользователя возвращает pending, но runtime оставляет confirmed=true. `confirmationStatusOf` возвращает confirmed.

В этом сценарии повторная цель не отправилась и серверного начисления нет. Дефект относится к ложному клиентскому статусу и изоляции сохранённого состояния.

Рекомендация: не менять владельца уже привязанной записи при захвате URL; изолировать записи по пользователю, а неизвестные/неподтверждённые записи связывать с ним только после корректного серверного ответа. Не использовать чужое подтверждение для баннера; асинхронные результаты старой сессии не должны обновлять новую.

## 3. P1: fallback хранения повторно отправляет уже завершённую цель

Файл: `src/lib/purchaseGoalRuntime.ts`, строки 100–131.

Воспроизведение: localStorage читается, но запись ключа очереди начинает бросать QuotaExceededError; sessionStorage работает. После первой успешной отправки sessionStorage содержит callback_completed. Следующее чтение предпочитает старую запись localStorage и теряет этот результат. Второй poll вызывает dispatchGoal повторно: две отправки одного VC invoice, несмотря на успешный первый callback.

Рекомендация: явно выбирать работоспособное хранилище и читать из того же источника, куда сохранён актуальный результат; при переключении согласовывать версии записей. Не позволять старому localStorage затереть более новое состояние sessionStorage/памяти. Добавить тест частичного сбоя, а не только полного отключения storage.

## 4. P1: блокировка без Web Locks истекает до завершения обработки

Файл: `src/lib/purchaseGoalRuntime.ts`, строки 238–258.

Воспроизведение в двух независимых runtime с общей localStorage и отключённым navigator.locks:

- t=0: первая вкладка захватывает lease на 15 секунд.
- t=11,5 с: счётчик готов, первая вкладка отправляет цель и ожидает callback.
- t=16 с: вторая вкладка считает lease просроченным и отправляет ту же цель.
- Первый callback приходит через 4,5 секунды ожидания, раньше своего timeout=8 секунд.

Итог: две отправки без неопределённого результата и без callback timeout. Это дополнительный дефект координации, а не описанный в отчёте риск повторения после сетевого timeout. Удаление lock в finally также не проверяет владельца.

Рекомендация: обеспечить владение блокировкой на весь срок ожидания счётчика, callback и retry; обновлять lease и проверять владельца перед отправкой и освобождением. Простое увеличение 15 секунд не решает неатомарный read/set между вкладками. Для fallback выбрать атомарный механизм либо явно ограничить его гарантию и исключить параллельную отправку активной попытки. Добавить отдельный тест двух вкладок без Web Locks.

## Миграция и границы проверки

`prisma/migrations/20261001210000_payment_event_analytics/migration.sql:3` предписывает применение **после** читающего новые поля кода. Это противоречит правильному порядку в отчёте и owner checklist: миграция **до** новой версии приложения. Исправить комментарий и подтвердить upgrade старой схемы с историческим PaymentEvent на отдельной тестовой БД. В этом ревью миграция на БД не применялась.

Не считать браузерный mock API независимой проверкой настоящего `/api/payment/status` или webhook. Его ответы в браузерной suite подменены. Не считать текущий тест «late webhook» проверкой задержки свыше 24 секунд: он возвращает pending только два раза. Длинную задержку и восстановление после появления сети стоит добавить в регрессионные сценарии.
